# 项目踩坑细节：面途 InterPace

> 这份文档记录**开发过程中真实踩到、并修掉的问题**，按"现象 → 影响 → 排查过程 → 根因 → 解决 → 验证 → 复盘"写，
> 目的是面试被问"你遇到过什么坑"时，能讲出**排查过程**而不是只报一个结论。
>
> 阅读约定：
> - 报错原文、命令、数字都来自当时的终端输出或代码注释，可直接引用；
> - 少量地方只能推断机理（例如 Docker 的 SNAT 细节），会明确标注"推断"；
> - 每条的"复盘"是**沉淀下来的预防手段**，也是这个项目里最值钱的部分。
>
> 分类：模型与 AI 链路 / 数据层 / 后端与测试 / 前端 / 部署与容器 / 安全与配额（含"拿不到真实 IP"）。

---

## 一、模型与 AI 链路（LangChain / 火山语音）

### 坑 1. 流式响应的 token 用量不在最后一帧，配额会静默失效

**现象**：按"取流式 chunk 的最后一块"去读用量，拿到的永远是 `None`，账本里记的是 0。

**影响**：**没有任何报错**。配额系统看起来在工作，实际永远拦不住人——典型的"静默失效"。这是全项目最危险的一类 bug。

**排查过程**：

1. 先怀疑是 provider 不给用量，把同一批文本分别用流式和非流式各调一次，**非流式能拿到**，说明不是 provider 的问题；
2. 再打印每一帧的 `usage_metadata`，发现**带用量的那一帧出现在中间**，不是最后一帧；
3. 结论：不能靠"最后一块"，必须累积。

**根因**：流式协议里，用量是随某一帧（token 统计出来的那一刻）一起下发的，位置不固定。

**解决**：在模型出口挂 LangChain callback，在 `on_llm_end` 里取用量：

```python
# app/agent/usage_callback.py:3-8（模块 docstring 就是这个坑的结论）
# - 实测这条链路**流式与非流式都能拿到真实用量**，只是流式时它不在最后一帧，
#   而在中间某一帧。所以必须挂回调累积，不能去读"最后一块 chunk"——
#   按最后一块读会得到 None，然后整个配额系统静默失效。
```

**验证**：真机跑一轮对话，`usage_records` 里 `prompt=435 / completion=34 / total=469`——数落账了。

**复盘**：**"取不到"要有声音**。`extract_usage` 取不到时返回全 0，但记 0 的同时保留调用计数并打 warning，
否则 provider 哪天改协议，配额会悄悄退化成"只按次数"（见 `usage_callback.py:55-60`）。

### 坑 2. 推理 token 计费且常占大头

**现象**：以为"输出 137 token"，结果账单按更多算。查用量明细发现 `reasoning_tokens` 是主力。

**影响**：按正文长度估成本会系统性低估；按字符估算更离谱。

**排查过程**：把 `usage_metadata.output_token_details.reasoning` 单独打印出来，实测一次输出
**137 token 里有 133 是推理**。

**根因**：推理模型的思维链也算输出 token 且要计费，但它不在返回给用户的文本里，容易被忽略。

**解决**：统计口径统一按 `total_tokens`，并把 `reasoning_tokens` 单独存一列便于分析
（`app/services/usage_quota_service.py` + `usage_records` 表）。

**验证**：`usage_records` 里四项（prompt / completion / reasoning / total）齐全，复盘场景可见推理占比过半。

**复盘**：**成本按"最坏口径"算，不要按"看得见的口径"算。**

### 坑 3. 提示词模板里的 JSON 花括号被当成模板变量

**现象**：调用时抛 `KeyError`，报的变量名是 JSON 里的某个字段。

**影响**：模板正文一放进 `ChatPromptTemplate` 就炸，整个出题/复盘链路不可用。

**排查过程**：报错的 key 名不是任何我们定义的变量 → 定位到模板正文里的 JSON 示例
（`{"items": []}`）被当成占位符 `{items}`。

**根因**：`ChatPromptTemplate` 用 `str.format` 语义解析 `{}`。

**解决**：模板里的裸花括号一律双写 `{{ }}`，再在注入时 `.replace()` 还原；并加回归用例守住。

```python
# tests 里专门留了一条：test_seed_templates_only_have_escaped_braces
# tests 里还有一条：test_quiz_template_renders_into_chat_prompt_template
```

**验证**：`test_seed_templates_only_have_escaped_braces` 后来**又抓了一次**——新增模板时忘了双写，测试立刻失败。

**复盘**：**这个坑反复出现**（至少三次），所以最终把它变成了一条**断言**而不是靠人记。同类问题：摘要注入时也踩过
（摘要文本里出现花括号会被解析成变量），最后改成用现成的 `SystemMessage` 直接塞，不走模板字符串。

### 坑 4. seed 是幂等的，导致"代码修好了但库里还是坏的"

**现象**：修好了模板正文的 bug、重启服务，问题依旧。

**影响**：看着代码是对的，运行行为是错的——非常消耗排查时间。

**排查过程**：直接查库看 `prompt_templates` 里那条 v1 的正文，发现还是带 bug 的旧版本。

**根因**：seed 逻辑是幂等的（"存在就跳过"），所以库里的旧正文不会被覆盖；而旧正文一旦被
`ChatPromptTemplate` 解析就会抛 `KeyError`。

**解决**：**原位修正库里那条 v1 正文**并刷新缓存，然后用 `ChatPromptTemplate.format()` 实测渲染成功。

**复盘**：**"种子数据"要区分"插入"和"同步"两种语义**。代码是权威、数据是副本时，就得有"数据版本"概念
（这个项目后来把提示词模板做成了可版本化管理的表）。

---

### 坑 5. 火山 TTS：`speaker` 放错层级，报错极具误导性

**现象**：

```
resource ID is mismatched with speaker related resource
```

**影响**：这个报错看起来像"资源包买错了/音色和模型版本不配"，实际是**参数放错了层级**，
浪费了好几轮探测（换音色、换资源包都无效）。

**排查过程**：反复试不同音色/资源包组合都报同一句 → 转而去比对官方示例的**参数位置**，
发现 `speaker` 必须放在 **StartSession 的 `req_params`** 里，放到 TaskRequest 就报这个错。

**解决**：`speaker` 放 StartSession 的 `req_params`；已写进 `.env.example` 的注释
（`VOLC_TTS_SPEAKER 必须与 TTS 模型版本配套`）防止后来人再绕一圈。

**复盘**：**第三方的报错文案经常指向错误的方向**。遇到"看起来像 A 实际是 B"的报错，要回到
**官方示例逐字段比对**，而不是顺着报错文案猜。

### 坑 6. 火山 TTS：不主动发 `FinishSession`，就永远等不到 `tts_end`

**现象**：最后一句音频合成完了，前端状态不收敛，一直在等 `tts_end`。

**影响**：面试间卡在"还在说话"，用户点不了下一句。

**排查过程**：抓事件流发现音频帧在流，但**句子结束 / 会话结束事件始终不来**；对照文档确认这是
"文本流式输入"接口，服务端不知道你写完了。

**根因**：文本流式输入没有隐式结束标记，服务端会一直等后续文本。

**解决**：文本发完后**主动发 `FinishSession`**，服务端才会补结束事件。

**复盘**：**"流式输入"必须显式收口**。同类问题在 `_receive` 上也踩过：原实现没有超时，
一次失败的合成把连接挂到调用方被强杀（实测卡了 180 秒），后来加了超时 + 回归用例。

### 坑 7. 火山 ASR：按"实时节拍"推流的约束

**现象**：把 14 秒音频**全速**推给流式 ASR，本该 3 句被切成 9 段、或者并成 1 段，VAD 分句乱掉。

**影响**：面试一轮被切碎，"一句话"这个概念不成立。

**排查过程**：先按全速推，分句异常 → 放慢到实时节拍（每 200ms 一包）后分句恢复正常。

**根因**：流式端点要求按实时节拍喂音频，服务端 VAD 依赖真实时间轴。

**解决**：

- **面试场景**（交互式）按实时节拍推，天然是一问一答；
- **录音转写场景**（一段 20 分钟录音）改用**整段识别端点**（`bigmodel_nostream`），
  否则 20 分钟录音要 20 分钟才转写完。实测 14.4 秒音频**约 2.4 秒出结果**，快一个数量级。

**复盘**：**同一个厂商的两条链路要按场景选**：实时交互用流式，离线文件用整段。

---

### 坑 8. 火山 ASR：整段识别会回大量空帧

**现象**：拿到响应就解析，文本是空的。

**影响**：录音复盘解析不出内容。

**排查过程**：打印每一帧，发现服务端在轮询，**只有 `is_last_package=True` 那一帧带完整文本**。

**解决**：读到 `is_last_package=True` 才算完，中间帧直接跳过。

**复盘**：**第三方"轮询式"响应要找到它的终止标志位**，不能想当然地取第一帧或最后一帧。

---

### 坑 9. 火山 ASR：判"一句话说完"要看 `definite`

**现象**：一轮面试被切成 9 次"最终结果"。

**影响**：面试官 Agent 收到半句话就开始回答，对话支离破碎。

**排查过程**：原逻辑是"有 `utterances` 就算一句说完"，打印中间结果发现**快速推流时中间结果也带 utterances**，
于是 3 句话被当成 9 次结束。

**根因**：`utterances` 存在 ≠ 这句已经定了。

**解决**：判停看 `utterances[-1].definite`（服务端 VAD 给的"这句确定了"标志），不能只看有没有 utterances。

**验证**：真机用官方示例音频（14.4 秒 / 72 个 200ms 包）识别正确，`utterances` 带
`start_time` / `end_time` / `definite`——**"服务端 VAD 能按句判停"这条设计前提成立**，不用自己写静音检测。

**复盘**：**"字段存在"和"字段代表的状态"是两回事**，要读语义标志位。

---

### 坑 10. 火山 ASR：`result.text` 是累计文本，还有 `0.0 or x` 的 falsy 坑

**现象**：第 2 句的识别结果里带着第 1 句；时间戳解析出 `-1`。

**影响**：转写文本重复、时间戳错位。

**排查过程**：

1. 对比 `result.text` 与 `utterances[-1].text`，确认前者是**会话累计文本**；
2. 时间戳异常定位到 `start_time = data.get("start_time") or 0` 这类写法——**起始时间本来就是 0.0，
   被 `or` 当假值吞掉**，走了兜底分支。

**解决**：优先取 `utterances[-1].text`；时间戳判断改成显式的 `is None`。

**复盘**：**`0` / `0.0` / `""` 是合法的业务值**，兜底写法要用 `is None` 而不是 `or`。
这是 Python 里非常经典的一类静默 bug。

---

### 坑 11. 帧头声明了 gzip，实际发的却是原始 PCM

**现象**：服务端解压失败。

**影响**：语音链路整条断。

**排查过程**：这是官方文档**自己列为排查第 1 项**的类型——先怀疑帧头/压缩，比对字节流确认
"声明 gzip 但没压缩"。

**解决**：在构建器内部统一压缩，别让"声明"和"内容"分离。

**验证**：假服务端测试端到端跑通。**注意**：写测试时在假服务端里**又犯了一次同样的错**
（声明 gzip 没压缩），说明这个错误确实容易发生，两个方向都值得留测试。

**复盘**：**协议层的问题要用"字节级对照"来查**，而不是看日志说成功。

---

### 坑 12. 字级/音素时间戳拿不到（**尚未解决**）

**现象**：即使 `enable_subtitle=True`，返回的 `words` 与 `phonemes` 都是**空数组**。

**影响**：口型同步的原计划（按音素驱动）做不了。

**排查过程**：开关分别放会话级、任务级、两边都放，多句文本也试过，**都是空**——确认是当前音色/账号的限制，
不是我们参数写错。

**解决（权宜）**：**降级为"前端音量分析兜底"**——口型按音频音量分档驱动。代码仍把 `words` / `phonemes`
原样往下传，将来换成支持字幕的音色可直接启用。

**复盘**：**要给"能力不可得"留降级路径，而不是卡死**。这条也说明了数字人三步走里
"先做纯语音、动效放第二步"的合理性——底层能力还没就绪时，不往上堆成本。

## 二、数据层（SQLAlchemy / MySQL / Alembic）

### 坑 13. `create_all` 永远不会修改已存在的表

**现象**：开发库里 `chat_messages.status` 的列注释还停留在旧版
（"0常规聊天，1面试转写入口"），而模型里早就加了新取值。

**影响**：各环境 schema 不一致；加列/改类型没有可回滚路径；出问题无法确认"库里到底是哪版结构"。

**排查过程**：对比"`create_all` 建的新库"和"用了很久的开发库"，发现同一张表的列注释不同——
因为 `create_all` 只**建缺失的表**，既不删、也不改。

**解决**：引入 **Alembic**，补基线迁移（用显式 DDL 固化 `create_all` 会建出的全部表），
并明确规则：**表结构的唯一权威是 `alembic/versions/`**。生产环境**不自动建表**，
必须显式跑迁移——"迁移忘跑"会立刻暴露，而不是被 `create_all` 掩盖成"表面能用、schema 是旧的"。

**验证**：对空库跑迁移 vs `create_all` 做**17 表 / 51 索引 / 24 外键零差异比对**。

**复盘**：**开发期的便利功能会在生产变成事故源**。`create_all` 省事的代价就是"schema 无人管理"。

---

### 坑 14. 比对 schema 的方法本身也踩了坑

**现象**：直接比 `SHOW CREATE TABLE`，报"6 张表不一致"。

**影响**：差点以为迁移写错了，实际是**比对方法**有问题。

**排查过程**：逐条看差异，发现全是**自动生成的外键约束名编号顺序**
（`xxx_ibfk_1/2/3` 指向不同列），结构其实一模一样。

**解决**：改用 `information_schema` 按"列 / 索引 / 外键指向"比对，才是有效判据。
另外发现**验证库的排序规则必须与目标库一致**，否则列上的 collation 会全都不一致。

**复盘**：**验证工具本身也要被验证**。一个只会喊"不一致"的比对器，比没有比对器更浪费时间。

---

### 坑 15. SQLAlchemy JSON 列：原地修改不会产生 UPDATE

**现象**：回填答案时"看起来写进去了"，查库发现没落库。

**影响**：用户答案丢失，且**没有报错**。

**排查过程**：测试先失败才暴露。定位到写法是"在原来的 dict 上原地改、再把同一个列表赋回去"——
SQLAlchemy 比较新旧值发现**相等**（因为是同一个对象），于是不产生 UPDATE。

**解决**：把每条 `dict()` 成新对象再整体赋回，让新旧值真的不同。

```python
# 反面写法：在同一个 dict 上原地改，再赋回同一个 list → 不产生 UPDATE
# 正确写法：qa_object = [dict(item) for item in new_items]  （新对象）
```

**复盘**：**ORM 不是"透明"的**，可变对象的原地修改是经典陷阱。这个坑直接影响了"面试记录追加一轮"的写法
（`interview_service._touch` 里也写了"JSON 列的原地修改不会被 SQLAlchemy 自动识别"）。

---

### 坑 16. 删会话撞外键（**同一个坑踩了 3~5 次**）

**现象**：删除会话请求整个失败，日志是外键约束报错。

**影响**：功能不可用（用户删不掉带题库/复盘/待确认画像的会话）。

**排查过程**：每次都一样——新加了一张指向 `sessions` 的表，但 `ChatService.delete_session`
没加对应的删除步骤。

**根因**：**加表时只改了生产代码，忘了改"删除流程"**。

- T5.3：题库（`quizzes` / `quiz_questions`）→ 删题目 → 删卷子 → 删消息/会话；
- T6.2：画像待确认（`profile_proposals`）→ 同一个坑；
- T8.2：面试复盘（`interview_evaluations`）→ 同一个坑，第三次。

**解决**：在 `delete_session` 里按依赖从叶子到根清理，响应里回传各表的删除条数
（`deleted_quizzes` 等），前端同步类型。

**复盘**：这个坑的根因是"**新表没有进入删除路径的清单**"。测试侧后来抽了共享 helper
`purge_user()`，让"加表忘了改清理"至少不会在测试里再漏。

---

### 坑 17. 删用户必然 `IntegrityError 1451`

**现象**：只要用户建过一次会话，删用户就报 `IntegrityError 1451`。

**影响**：账号注销功能完全不可用。这个问题**不是新引入的**，是历史遗留，被新工作撞出来。

**排查过程**：查 `information_schema` 发现 `users` 被 **10 张表以 `NO ACTION` 外键引用、没有任何级联**，
而 `UserService.delete_user` 原来只有一句 `db.delete(user)`。

**解决**：按依赖从**叶子到根**逐表清理，最后删用户行，事务提交后再 best-effort 回收对象存储。

**验证**：删除测试改成**泛化断言**——遍历所有带 `user_id` 的表确认都清空了
（`CASCADE_EXEMPT_TABLES = {"usage_records"}` 是唯一例外，因为它是成本账本，刻意保留）。

**复盘**：**"删除"是最容易漏的路径**。单个 `db.delete` 看着优雅，但数据库没有级联时它就是错的。
把测试写成"遍历所有相关表"而不是"抽查某张表"，以后加表忘了改删除逻辑会被自动抓到。

---

### 坑 18. 画像缓存改"从明细重建"后，升级会抹掉旧数据

**现象**：升级后第一次写入，老数据被清空。

**影响**：**真实数据损失**——实测开发库有 75 行画像属于这种情况（共 173 条）。

**排查过程**：缓存改成"从明细表重建"后是**覆盖**语义，而 T9.2 之前的数据只躺在旧的 JSON 列里，
明细表是空的 → 重建 = 用空数据覆盖。

**解决**：写一次性回填脚本（`scripts/backfill_user_memories.py`）把旧 JSON 列灌进明细表，
并做幂等（可重复执行）。

**复盘**：**"改数据来源"是最高风险的重构**。只要有旧数据路径，就要问一句"存量数据怎么办"，
并且**在开发库上先跑一遍看行数**，别直接上生产。

## 三、后端与测试

### 坑 19. 限流窗口跨用例累计：单跑绿、全套炸

**现象**：新增 4 个用例后，注册相关的 3 个用例报 429；**单独跑那个文件永远是绿的**。

**影响**：非常隐蔽——很容易被当成"偶发"，或者错误地去改业务限流阈值。

**排查过程**：算了一下，全套跑下来注册接口被调用 8 次，**超过了"每分钟 5 次"的限流**。
限流是按时间窗 + IP 计数的，进程内状态被多个用例共享。

**解决**：给 `app/core/rate_limit.py` 加 `reset_rate_limit_windows()`（明确标注主要给测试用），
在 `conftest.py` 里加 **autouse 夹具**每个用例前清空窗口。

**验证**：连续跑两次都是 **33 passed**（当时），确认稳定。

**复盘**：**"单测绿≠全绿"的一个典型来源是进程级共享状态**（限流、缓存、随机种子）。
这类问题的解法是"给测试提供重置钩子"，而不是改业务阈值。

### 坑 20. 新加的路由 404，因为后端进程加载的还是旧代码

**现象**：页面上打开笔记本全部 404，日志显示 `GET /notes` 与 `POST /notes` 都是 404。

**影响**：前端看着像"接口没实现"，实际是后端没重启。**这个坑同一个项目里出现了 3 次**。

**排查过程**：对照时间线——后端进程 14:00 启动，`/notes` 路由是之后加的，而 uvicorn 没开 `--reload`。

**解决**：后端统一改成本地开发用 `uvicorn app.main:app --reload` 启动，后续改动自动热加载；
后来进一步收敛进 `dev.sh`（一键启停 + 状态里显示进程的 `APP_ENV`）。

**复盘**：**"改了代码行为没变"先看进程启动时间和是否热加载**，别一头扎进业务逻辑。

## 四、前端

### 坑 21. `Prism is not defined`——只在生产构建里出现

**现象**：开发模式一切正常，**生产构建**后打开聊天页报：

```
ReferenceError: Prism is not defined
```

**影响**：开发自测全绿、上线就炸。是"验证环境 ≠ 目标环境"的典型。

**排查过程**：

1. **先在真实构建产物上复现**（不是读代码猜），确认只有生产构建才炸；
2. 定位到报错来自打包后的某个 chunk，发现代码高亮的语言包引用的是**全局** `Prism`；
3. 再看 Prism 核心挂全局那句：`typeof global !== 'undefined' && (global.Prism = Prism)`——
   **浏览器里没有 `global`**（那是 Node 的东西），这句永远不执行；
4. 解释"为什么开发模式正常"：Vite 的 CJS 互操作会补上 `global`；
5. 为什么只有生产炸：打包后语言包先求值、全局还不存在。

**解决（三步）**：

1. `src/utils/prism-setup.ts` 显式挂到 `globalThis`，并**保证它在所有语言包之前求值**；
2. `markdownUtil.ts` 里把 `import './prism-setup'` 排在语言包之前；
3. `vite.config.ts` 里让 **prismjs 不参与手动分块**（跨 chunk 的加载顺序不可控，拆开就会复发）。

**复盘**：**`pnpm run build` 成功、开发模式正常，都不代表生产产物没问题**。
后来把"在真实产物上打开关键页面、断言控制台无 error"写进了流程。

### 坑 22. 429 的英文原文被直接弹给用户

**现象**：页面弹窗提示 `Request failed with status code 429`。

**影响**：用户不知道发生了什么，也不知道该怎么办——演示环境本来就是要"友好地告诉用户额度用完了"。

**排查过程**：后端其实返回了中文 `message`（"演示环境的体验额度已用完…"），但组件里用的是
`ElMessage.error(error.message)`，即 axios 的英文原文；而且拦截器和组件会**各弹一次**。

**解决**：新增 `src/utils/errorMessage.ts`：

- `notifyError()` **优先用后端的 `message`**（比按状态码套模板准确）；
- **跳过拦截器已经提示过的**，避免一次失败弹两个框；
- 全项目不再直接 `ElMessage.error(error.message)`。

**验证**：真机 `APP_ENV=demo` 触发超额，页面提示正确（不再是英文原文）。

**复盘**：**错误提示是产品的一部分**，尤其是演示环境。统一走一个出口 + 去重，
比在每个组件里各写一套更可靠。

## 五、部署与容器

### 坑 23. 构建机与服务端 CPU 架构必须一致

**现象**：在 Apple Silicon（arm64）Mac 上构建、`docker save` 出来的镜像传到 amd64 云服务器，
启动时报：

```
! minio    The requested image's platform (linux/arm64) does not match the detected host platform (linux/amd64/v3)
! redis    The requested image's platform (linux/arm64/v8) does not match the detected host platform (linux/amd64/v3)
! backend  The requested image's platform (linux/arm64) does not match the detected host platform (linux/amd64/v3)
dependency failed to start: container interpace-redis-1 is unhealthy
```

**影响**：整栈起不来，而且**只有到服务器上才会暴露**。

**排查过程**：先确认服务器架构（amd64），再 `docker image inspect` 看本地镜像架构（arm64）——
一眼看出不匹配。接着试交叉构建：

| 想产出 amd64 镜像 | 能否在 arm64 Mac 上交叉构建 | 说明 |
| --- | --- | --- |
| 前端镜像（node + vite） | ✅ 可以 | 实测产出 `amd64/linux`，约 90 秒 |
| **后端镜像（`uv sync`）** | ❌ **不行** | `uv` 是 Rust 二进制，QEMU 下直接段错误：`qemu: uncaught target signal 11 (Segmentation fault)` |
| python / node / nginx 的 amd64 变体 | ✅ 能跑 | 说明问题只出在 `uv` 这个二进制上 |

**根因**：`uv` 在 QEMU 用户态模拟下段错误，所以 arm64 机器上**产不出完整的 amd64 后端镜像**。

**解决**：部署流程改成**在服务器上构建**（服务器本身就是 amd64，原生构建无架构问题），
源码走 git：本机 push、服务器 clone / pull。**代价**：服务器构建慢（2 核 2G），要先加 swap、
先 build 再 up（构建时别跑着 MySQL）。

**复盘**：**架构不匹配是"验证环境 ≠ 目标环境"最贵的一种表现形式**（见坑 24）。
现在传输前必做 `docker image inspect <镜像> --format '{{.Architecture}}'` 自检。

### 坑 24. "模拟服务器"和构建机是同一台机器 → 验证等于没做

**现象**：离线镜像传输流程在本地"完整验证通过"，到真服务器上照样炸。

**影响**：白做一轮验证，还产生了"已经验过了"的错误信心。

**排查过程**：复盘验证过程——当时用另一个目录 + 另一个项目名模拟服务器，
**但仍在同一台 arm64 Mac 上**。于是 arm64 镜像在 arm64 上跑得好好的，**架构问题完全没暴露**。

**根因**：验证环境（arm64）与目标环境（amd64）不一致。

**解决**：把这条写进文档，并**明确标注那次验证的适用范围**——"只证明流程本身通，
不能证明产物能在 amd64 服务器上跑"。

**复盘**：**验证的结论要带上"在什么环境验的"**。否则"我验过"三个字会误导后面所有人（包括自己）。

### 坑 25. `docker load` 会覆盖同名标签

**现象**：离线传镜像后，服务器上原本正确架构的 `mysql:8.0` / `redis:7-alpine` / `minio` 起不来。

**影响**：**静默替换**——旧镜像连悬空镜像都找不回来（没保留其他标签）。

**排查过程**：第一版流程把第三方镜像一起打了个包，`docker load` 之后这三张原本是 amd64 的镜像
被包里的 arm64 版本**静默覆盖**。

**解决**：**只打包应用镜像**（backend / frontend），第三方镜像一律让服务器自己
`docker compose pull` 或复用已有的。应用镜像包也从 5 个（562 MB）降到 2 个（279 MB）。

**复盘**：**"批量操作"要看清作用域**。`docker load` 不是"新增"，是"覆盖同名标签"。

### 坑 26. Nginx 缓存上游 IP → 更新后端后持续 502

**现象**：只重建后端（发版时最常见），站点开始 **502，直到手动重启 Nginx**。

**影响**：每次发版都可能中断服务。

**排查过程**：Nginx **只在启动时解析一次**上游主机名并缓存 IP；后端容器重建后拿到新 IP，
Nginx 还往旧 IP 转发。

**解决**（`deploy/nginx.conf`）：

```nginx
resolver 127.0.0.11 valid=10s ipv6=off;
set $upstream_backend backend;
proxy_pass http://$upstream_backend:8000;   # 变量形式，运行时重新解析
```

**验证（决定性）**：删掉后端容器 → 起一个**占位容器抢走旧 IP** → 重建后端（拿到新 IP）→
**不重启 Nginx**，连续请求全部 200。没有这个配置，Nginx 会一直打在那个占位容器上。

**代价**：解析缓存过期那一刻的请求可能拿到一次 502（可接受的权衡——比"永久 502 直到重启"好得多）。

**复盘**：**反代类组件要区分"启动时解析"和"运行时解析"**。顺带把 frontend 的 `depends_on`
从 `service_started` 升级为 `service_healthy`，否则后端还在跑迁移时 Nginx 就接请求，用户看到一片 502。

### 坑 27. SSE 被代理缓冲 / WebSocket 缺升级头

**现象**：

- 文字流式对话"卡住不动，最后一次性冒出一大段"；
- 语音面试线上连不上（本地开发却正常）。

**影响**：两个核心体验链路在线上直接废掉。

**排查过程**：

- SSE：现象是"攒批"，直接指向 Nginx 的**代理缓冲**；
- WebSocket：本地开发靠 **Vite 代理的 `ws: true`** 顶上了，**线上没有这层兜底**——
  排查时特意回到"开发能过、线上不能过"的差异点，锁定到握手头。

**解决**（`deploy/nginx.conf`）：

```nginx
# SSE 那段
proxy_buffering off;
proxy_cache off;

# WebSocket 那段（必须）
proxy_http_version 1.1;
proxy_set_header Upgrade $http_upgrade;
proxy_set_header Connection "upgrade";
```

**复盘**：**开发环境的便利功能（如 Vite 代理）会掩盖线上的真实要求**。
凡是"本地能跑、线上不能跑"，先列出两者的差异清单，从差异里找。

### 坑 28. MinIO 镜像地址漂移 + 不同机器网络差异

**现象**：`minio/minio:latest` 在开发机上报
`repository does not exist or may require 'docker login'`，在云服务器上却能正常拉。

**影响**：镜像拉不到，整栈起不来。

**排查过程**：

- `minio/minio:latest`（Docker Hub）：**有的网络能拉，有的不行**——取决于网络；
- `quay.io/minio/minio:latest`：官方主推，但**匿名拉取被拒**，要先 `docker login quay.io`。

**解决**：镜像地址做成**可配置**（`image: ${MINIO_IMAGE:-minio/minio:latest}`），
哪个能拉用哪个，不改 compose 文件。服务器上最终用的就是 `minio/minio:latest`。

**复盘**：**别把"我这能拉"当成结论**。外部镜像地址会漂移，配置化是唯一稳的做法。

### 坑 29. Dockerfile 没 `COPY config`，配额静默失效

**现象**：容器里的演示配额没生效，**退回"不限制"**。

**影响**：演示环境的成本防护在**无人察觉**的情况下失效——比报错危险得多。

**排查过程**：后端读配额文件用的是镜像内路径 `/app/config/demo_limits.json`，
而 Dockerfile 原来没把 `config/` 复制进镜像。

**解决**：补 `COPY config ./config`，并实测容器内 `APP_ENV=demo` 时
`is_enforced=True`、降本开关生效。

**复盘**：**"读不到配置就退回默认值"是个危险的设计模式**——默认值是"不限制"时，
故障表现为"看起来一切正常"。凡是安全/成本相关的配置，读不到应该**显式报错或至少打 ERROR**。

### 坑 30. NPM 的默认值：上传 413、慢接口 504

**现象**：上传 PDF/录音直接 413；生成复盘有时候 504。

**影响**：附件与复盘两个功能在线上不可用。

**排查过程**：我们自己的 Nginx 里虽然配了 `client_max_body_size 100m`，
但请求**先被外层的 Nginx Proxy Manager 拦下**——NPM 默认只有 1MB；
同理 NPM 默认读超时只有几十秒，而我们这几条是"一次模型调用"级别的慢接口。

**解决**：在 NPM 的 Proxy Host → Advanced 里补：

```nginx
proxy_buffering off;
proxy_cache off;
client_max_body_size 100m;
proxy_read_timeout 300s;
proxy_send_timeout 300s;
```

**复盘**：**多了一层代理，就等于多了一层默认值**。排查"配置明明写了却不生效"时，
先确认请求链路上有**几层**代理、每一层的默认值是什么。

### 坑 31. 冒烟脚本第一次跑就抓到一个真实部署缺陷

**现象**：容器里附件上传返回 **500**。

**影响**：功能在本地完全正常，只在容器编排下坏——典型的"部署缺陷"。

**排查过程**：冒烟脚本是按顺序打每个接口的，到上传这一步 500；
对比本地与容器的环境变量，发现 compose 里 MinIO 用的是 `MINIO_ROOT_USER/PASSWORD`，
而后端读的是 `MINIO_ACCESS_KEY/SECRET_KEY`，**没做映射**，后端退回了默认的 `minioadmin`。

**解决**：在 compose 里显式映射：

```yaml
MINIO_ACCESS_KEY: ${MINIO_ROOT_USER}
MINIO_SECRET_KEY: ${MINIO_ROOT_PASSWORD}
```

**复盘**：**"配置项名字对不上"是最容易漏的部署 bug**，而且本地开发完全测不出来
（本地直接读 `.env`）。所以冒烟脚本**必须经过 Nginx、在容器里跑**，才抓得到这类问题。

### 坑 32. `docker compose up -d` 不会重新构建

**现象**：改了源码、`docker compose up -d` 之后，行为没变。

**影响**：误判成"代码没生效/有缓存"，浪费排查时间（本项目踩了不止一次）。

**排查过程**：`up -d` 只在镜像**不存在**时才构建；镜像已存在就复用它。

**解决**：改源码后必须 `docker compose up -d --build`（本项目服务器上的做法是
`git pull` 后 `docker compose build <服务> && docker compose up -d`）。

**复盘**：**"部署命令"和"构建命令"要分清**。这条也解释了为什么"代码更新了还需要 build 吗"是个高频问题。

### 坑 33. 服务器上 `http://<公网IP>:8080` 访问不到

**现象**：容器里 `curl -I http://127.0.0.1:8080/` 返回 200，但外网访问不了。

**影响**：以为服务没起来，实际是端口/绑定问题。

**排查过程**：

1. `docker port interpace-frontend-1` → `80/tcp -> 0.0.0.0:8080` —— 映射没问题；
2. 容器内/宿主机 `curl 127.0.0.1:8080` → 200 —— 服务正常；
3. 于是问题在外网入口：云服务器**安全组/防火墙没有放行 8080**。

**解决**：正式入口走域名 + NPM 反代（443），不需要对外暴露 8080；
本地验证时用 `WEB_PORT` 指定端口，需要时再单独放行。
`.env.example` 里也留了 `# WEB_PORT=127.0.0.1:8088`（只绑回环，不对公网暴露）。

**复盘**：**分三层确认"服务起没起"**：容器内 → 宿主机 → 外网。
三层各查一次，能直接把问题定位到"应用 / 映射 / 网络策略"的哪一层。

### 坑 34. `pnpm` 版本差导致容器内构建失败

**现象**：本地 `pnpm run build` 正常，容器里构建报 `ERR_PNPM_IGNORED_BUILDS`。

**影响**：CI/服务器构建失败，本地完全复现不了。

**排查过程**：`corepack` 在容器里装了最新版 pnpm，而 **pnpm 10+ 遇到"被忽略的构建脚本"会直接报错退出**。

**解决**：前端 Dockerfile 里锁定 `npm install -g pnpm@9.1.0`（与开发机一致）。

**复盘**：**"环境版本差导致的构建失败"最省事的解法就是把版本钉死**，而不是去改代码适配。

### 坑 35. Redis 的 `--save` 要吃两个参数

**现象**：Redis 容器起不来，日志报 `Bad directive`。

**影响**：容器 unhealthy，依赖它的服务被拖死（`dependency failed to start`）。

**排查过程**：compose 里写的是 `--save=`，Redis 把它当成"`save <空>`"，
于是**把后面的 `--appendonly=no` 吃掉当第二个参数**，直接报错。

**解决**：`--save` 写成**两个独立参数**（`--save` + 空串）：

```yaml
command:
  - redis-server
  - --maxmemory
  - ${REDIS_MAXMEMORY:-96mb}
  - --maxmemory-policy
  - allkeys-lru
  - --save
  - ""              # 必须独立写，不能写成 --save=
  - --appendonly
  - "no"
```

**复盘**：**命令行参数的"等号写法"和"空格写法"不总是等价**。踩一次之后把结论写进注释，别人（和自己）不用再踩。

---

### 坑 36. Shell 脚本里 `$var` 紧跟中文标点 → `unbound variable`

**现象**：脚本报 `pid）: unbound variable`。

**影响**：`dev.sh` / `backup.sh` 直接中断。

**排查过程**：`"（PID $pid）"` 里的 `$pid）`——**中文括号被当成变量名的一部分**，
于是去找一个叫 `pid）` 的变量，自然找不到。

**解决**：三个脚本里所有"变量 + 中文标点"的写法统一改成 `${var}`：`"（PID ${pid}）"`。

**验证**：`dev.sh` 的 `start` / `stop` / `status` 全部实测通过。

**复盘**：**这个是第二次踩**（第一次在 `deploy/backup.sh`）。规则化成"变量一律用 `${}`"之后就不会再犯——
属于**用约定消灭一类问题**，而不是记一个特例。

### 坑 37. `kill` 父进程停不干净

**现象**：`dev.sh stop` 报"已停止"，但端口没释放、服务还在跑。

**影响**：再 `start` 时报"端口被占用"，或者悄悄跑着旧代码（与坑 20 叠加）。

**排查过程**：`uvicorn --reload` 和 `vite` 都会 **fork 出真正干活的子进程**。
只 kill 父进程，子进程会被 **reparent 到 init**，之后 `pkill -P 父PID` 就找不到它了。

**解决**（`dev.sh:215-245`）：**先 `pgrep -P` 记下子进程，再杀父进程**，
另外保留"按端口兜底收掉"作为最后防线（`kill -TERM` → 等 → `kill -9`）。

**验证**：`stop` 后两个端口都释放、无残留进程；再 `start` 恢复正常。

**复盘**：**"进程树"要当整体处理**。写停服脚本时，先想清楚"这个命令有几个进程"。

## 六、安全与配额

### 坑 38. 配额配置没限定环境，本地开发把自己卡死了

**现象**：本地开发也被配额拦截，后台抽取被静默关掉。

**影响**：开发效率被打断，且现象诡异（像"功能没实现"）。

**排查过程**：最初只写了无条件的 `enabled=true`，**没有限制生效环境**。

**解决**：配置里加 `environments`（默认 `["demo"]`）——开发/测试/正式都不受影响，
只有演示环境生效。

**复盘**：**"全局开关"要有作用域**。功能开关如此，配额开关更是如此。

---

### 坑 39. 限流取 `X-Forwarded-For` 的第一个值 → 可以被随便伪造

**现象**：攻击者每个请求换一个假 `X-Forwarded-For`，限流完全失效。

**影响**：**安全漏洞**——配额与限流的前提被破坏。

**排查过程**：原来的限流取 XFF 的**第一个**值；而 Nginx 用的是
`$proxy_add_x_forwarded_for`（**保留客户端传的值、在末尾追加真实 IP**），
所以第一个值就是客户端自己写的，**随便伪造**。

**根因**：混淆了两个层次——

- `$remote_addr` / `request.client.host` 来自 **TCP 连接的对端地址**，建立连接后**伪造不了**；
- `X-Forwarded-For` / `X-Real-IP` 只是**普通 HTTP 头**，客户端想写什么就写什么。

**解决**：

1. Nginx **改成覆盖**：`proxy_set_header X-Forwarded-For $remote_addr;`
   （SSE / WebSocket / 通用 `/api/` 三处都改），后端看到的值永远只有一个；
2. 新增 `app/core/client_ip.py`，按"不可伪造优先"取值：
   `X-Real-IP` → XFF **最后一段** → 直连的 `request.client.host`；
3. 加开关 `TRUST_PROXY_HEADERS`（默认 `false`，部署到 Nginx 后面才打开）；
4. HTTP 与 WebSocket **共用同一套口径**（两边不一致会让同一用户被算成两个 IP，配额各算一份）。

**验证**：临时起一套 Nginx + 回显服务（用完即删），客户端带伪造的
`X-Forwarded-For: 1.2.3.4` 与 `X-Real-IP: 9.9.9.9` 请求，
后端实际收到的两个头都是 TCP 对端的真实地址——**伪造值被完全丢弃**。

**复盘**：**"谁能定义我是谁"这件事必须由可信边界决定**。默认不信任转发头，
只有"请求确实来自我们自己的代理"时才认——这个边界就是 `TRUST_PROXY_HEADERS`。

---

### 坑 40. 演示环境拿不到真实客户端 IP（NPM 转发到了公网 IP）★

**现象**：服务器上 `usage_records` 里 9 行记录的 `client_ip` **全是同一个值**
`111.231.94.236`——而这正是**服务器自己的公网 IP**，不是任何访客的地址。

**影响**：**所有访客共用一个配额桶**。第一个人正常用，第二个人一来就被 429 拦掉；
反过来也可能一个人把所有人的额度刷完。这直接让"按 IP 限流"这个防护失效——
和坑 39 是同一个目标（配额正确性），但成因完全不同：
坑 39 是"取了可伪造的头"，这条是"**我们根本没拿到真实 IP**"。

**排查过程**：

1. 先查库确认现象：`SELECT client_ip, COUNT(*) FROM usage_records GROUP BY client_ip;`
   —— 只有一行、值等于服务器的公网 IP，说明"每个人"被记成了同一个来源；
2. 排除"应用取错头"：`client_ip.py` 的取值顺序是对的（`X-Real-IP` 优先），
   说明问题不在这层；
3. 往上追一层：这是**容器编排 + NPM 反代**的链路上出的问题。
   当时启动容器**没有使用 `docker-compose.npm.yml`**，NPM 的 Proxy Host 直接把
   **Forward Hostname 填成了服务器的公网 IP**（`111.231.94.236`），而不是内网网关/容器名；
4. 于是整条链路变成：访客 → NPM → **再绕到本机公网 IP:8080** → 我们的 Nginx。
   请求到达我们 Nginx 时，**对端地址变成了那个公网 IP**（Docker 出栈做了 SNAT，推断）；
5. 关键一击在这：`deploy/nginx.conf` 里的 realip 模块配的是
   `set_real_ip_from 10/8, 172.16/12, 192.168/16`——**只信任私网对端**。
   对端是公网 IP，不在信任表里，于是 **realip 忽略了（其实是正确的）`X-Forwarded-For`**，
   `$remote_addr` 保持为那个公网 IP；后面 `proxy_set_header X-Real-IP $remote_addr`
   就把这个公网 IP 一路写到了后端 → 落进 `client_ip`。

**根因**：NPM 的"Forward Hostname"填成了**公网 IP**，导致请求在我们 Nginx 看来
来自一个**不可信的（公网）对端**，realip 因此不采信 XFF，真实 IP 在最后一段被丢掉。

**解决**：把 NPM 的 Forward Hostname 改成**内网网关地址**（`172.x.x.x` 这个 docker 网段，
也就是我们 Nginx 发布端口在宿主机上的内网入口），而不是公网 IP / 域名。
这样对端落回 `172.16.0.0/12` 信任网段内，realip 才会把 `X-Forwarded-For` 还原成真实客户端 IP。

**验证**：改完再跑，同一个接口产生的多条记录里 `client_ip` **不再全相同**，
新记录能带上真实访客地址（`SELECT client_ip, created_at FROM usage_records ORDER BY id DESC;` 逐行核对）。

**复盘**：

- **"代理在哪里"决定"IP 从哪来"**。反代的 Forward Hostname 必须指向**内网路径**，
  填公网 IP 会把整条链路绕出去、把来源 IP 弄丢；
- **realip 是"按对端校验 + 只在信任网段生效"的**（本项目实测确认过）：
  `set_real_ip_from` 只列私网，于是"从公网直连过来伪造 IP"是无效的（安全），
  但"代理从公网绕进来"也会被同样地拒绝（可用性）——**同一个机制的两面**；
- **排查顺序应该是"先看数据、再往上追一层"**：先确认 `client_ip` 不合常理，
  再依次排除"应用取头 → 我们 Nginx → NPM → Docker 网络"，而不是一上来就改代码；
- 文档里给了**一条能复现的验证命令**（查 `usage_records` 的 `client_ip` 分布），
  以后再出这类问题，不用重新想一遍。

> 关联：`docs/部署/docker部署.md` 的 5.5 节（客户端 IP 的传递）。
> 那条给出了正常的验证方法——带 `X-Forwarded-For: 203.0.113.99` 发一轮对话，
> 查 `usage_records.client_ip` 应该就是 `203.0.113.99`；**如果记的是 `172.x.x.x`（容器网段），说明 realip 没生效**。
> 本次的特殊之处是：记录的是**公网 IP**，指向的是"代理绕了公网"这个方向。

### 坑 41. "后端端口暴露"会让配额的所有前提失效

**现象**：如果把后端 8000 直接 `ports: 8000:8000` 映射到公网，攻击者可以绕过 Nginx 直连后端。

**影响**：`$remote_addr` 变成攻击者自己的地址可随意伪造判断；IP 配额与限流全部失去意义。

**排查过程**：这是设计时主动识别的（不是踩了才知道），在 T12.4 的"IP 不可伪造"结论里就写成了硬要求。

**解决**：**后端只 `expose`，不 `ports`**——只在容器网络内可达；
MySQL / Redis / MinIO 同理。只有 frontend（Nginx）发布端口。
MySQL 若要本地连库，**只绑宿主机回环**：`"127.0.0.1:3307:3306"`，走 SSH 隧道连，不动云防火墙。

**验证**：`docker compose ps` 确认端口映射；从外网扫后端端口应该连不上。

**复盘**：**安全设计的核心是"减少入口"**。少一个对外端口，就少一类"绕过前面所有防护"的可能。

### 坑 42. 实际最先触发的不是"单 IP 300 万"，而是全局日预算

**现象**：真机验证时，先触发的不是"每 IP 300 万"，而是**全局日预算 50 万**。

**影响**：不是 bug，但容易误判成"单 IP 配额没生效"。

**排查过程**：把两个额度的语义摊开看——

| 额度 | 管什么 | 何时触发 |
| --- | --- | --- |
| 每 IP 累计 300 万 | **长期**防同一个人反复来刷 | 跨天累积，单日很难到 |
| 全局每日 50 万 | **单日**总支出兜底 | 通常先触发 |

两者管的是不同的事，**先触发的那个只是"更早到达的约束"**。

**解决（配置取舍）**：如果希望"单个 IP 的 300 万"成为真正先触发的硬限制，
把 `global.daily_token_budget` 提到 300 万；想更省则调到 20 万。
配置是 JSON 文件、**热重载**（最多 5 秒生效），不用重启。

**复盘**：**多个配额叠加时，要画清楚"谁先到"**，否则上线后会被用户反馈搞晕。
这个数字本质上是"你每天愿意为演示环境花多少钱"，得自己定一个。

## 附：这套坑的共同规律

把上面这些分类归纳一下，其实反复出现的只有三条根因：

1. **验证环境 ≠ 目标环境**——arm64 上构建、在 arm64 上验证、开发模式正常、假服务测语音，
   都属于这一类（坑 23/24/21/5~12）。
2. **静默失效比报错危险**——用量取不到记 0、配额文件读不到退回不限制、
   `create_all` 不报错但 schema 是旧的、JSON 原地修改不产生 UPDATE、realip 不生效但请求照常返回 200
   （坑 1/15/13/29/40）。所以后来养成的习惯是：**关键路径要有"能报警的断言"**。
3. **"加了一个东西"必须回头检查它的所有关联路径**——加表要改删除、加路由要重启、
   加代理要多一层默认值、加转发头要考虑信任边界（坑 16/17/20/30/39/40）。

以及一条工程习惯：**每个结论都留一条能复现的命令**——查 `usage_records`、`docker image inspect` 看架构、
`nginx -T` 看生效配置、冒烟脚本、配额查询 SQL。
这比"我记得是这样"可靠得多，也是从这个项目里带走的最主要的东西。
