## 一句话

一个把「AI 模拟面试」做完整闭环的项目：**多轮追问 + 语音对话 + 自动复盘 + 长期记忆**，
从 0 到 1 独立完成设计、开发、测试与容器化部署，后端跑在一台 2 核 2G 的轻量云服务器上。

## 项目背景

求职者练面试最大的问题是**没有反馈闭环**：

1. 自言自语没人追问——答不上来的地方会不自觉跳过，越练越熟的只有本来就会的部分；
2. 练完不知道差在哪——"感觉还行"没法指导下一步改什么；
3. 换个工具就"不认识你"——每次都要重新自我介绍，同类问题反复被指出，聊完就忘。

面途针对这三点分别给了三样东西：**会追问的面试官 Agent**、**结构化复盘**、
以及一套**跨会话的长期记忆**（越用越贴着你）。

## 技术栈

| 层 | 选型 |
| --- | --- |
| 前端 | Vue 3、Vite、TypeScript、Pinia、Element Plus；AudioWorklet 采集 PCM + Web Audio 播放 |
| 后端 | Python、FastAPI、SQLAlchemy 2.0、Alembic、Pydantic v2；路由 / 校验 / 业务 / 数据四层分层 |
| 智能体 | **LangGraph + LangChain**：对话编排图 + 记忆抽取状态图（含条件分支） |
| 存储 | MySQL 8（含 `FULLTEXT ... WITH PARSER ngram` 中文检索）、Redis（模板缓存）、MinIO（对象存储） |
| 语音 | 火山引擎 ASR（双向流式 WebSocket）+ TTS（双向流式，PCM 24k） |
| 部署 | Docker Compose（5 容器）、Nginx / Nginx Proxy Manager、Let's Encrypt、Alembic 迁移 |

## 个人职责

**架构与后端（主要）**

- 设计并实现**四层分层架构**（路由 / 校验 / 业务 / 数据），接口统一 `/api/v1` 前缀；
  业务逻辑不进路由，公共能力（鉴权、错误响应、限流、客户端 IP）统一抽成 core 层复用。
- 用 **LangGraph** 编排智能体：对话侧是"提示词 → 模型"的单节点图（便于换模型与加节点）；
  记忆侧是带**条件边**的状态图（抽取 → 校验 → 落库，容量超限时先走整合分支）。
- 设计 **select_model → Agent/Scene 的注册表**（`scene_registry`），把"模式"从散落的 `if-else`
  收敛成一张表：新增模式只加一行，前端只提交一个数字。
- 实现**三层长期记忆**（L1 明细 / L2 方法 / L3 检索），含来源权重合并、容量上限与自动整合、
  待确认审批、变更日志与用户级隔离（详见下文"技术亮点"）。
- 实现 **SSE 流式对话**与**停止**（双保险：显式停止接口 + `AbortController`），
  停止后已生成内容照常落库并标记状态；长会话用**渐进式摘要压缩**控制上下文成本。
- 实现**语音面试链路**：火山 ASR（按句开会话、VAD 分句）→ 面试官 Agent → TTS 流式合成，
  全链路走一条 WebSocket；API Key 只留在后端，不下发浏览器。

**工程化与交付**

- 数据库变更全部走 **Alembic 迁移**，并对空库跑迁移与 `create_all` 做过
  **17 表 / 51 索引 / 24 外键的零差异比对**，把"schema 无人管理"的历史问题收敛掉。
- 后端测试从 0 补到 **251 个用例**，覆盖每个路由的正常路径与错误路径
  （鉴权失败、越权、资源不存在、参数校验、幂等、级联删除的泛化断言）。
- 写了**上线冒烟脚本**（在容器内跑、经 Nginx 反代、覆盖 13 项检查），
  第一次跑就抓出一个真实部署缺陷（对象存储凭据未映射导致上传 500）。
- 容器化落地到 **2 核 2G** 的服务器：多阶段镜像、非 root 运行、单 uvicorn worker，
  实测五个容器常驻内存约 **434 MB**。

**前端**

- 路由级懒加载 + 大依赖手动分块：入口包从 **2112 KB 降到 57 KB**（gzip 714 KB → 21.6 KB）。
- 统一错误提示链路（优先展示后端中文 `message`、拦截器与组件间去重），
  把 `Request failed with status code 429` 这类英文原文换成"额度已用完/请求过于频繁"。

## 技术亮点（面试可以重点讲这四条）

### 1）三层长期记忆：不是"存个画像"，而是分层管理不同生命周期的信息

| 层 | 存什么 | 存哪 | 何时注入 |
| --- | --- | --- | --- |
| L1 明细 | 技能 / 薄弱点 / 答题方法，带掌握度、来源、证据次数 | `user_memories` | 每次回答前挑相关的注入 |
| L2 方法 | 反复出现的表达问题沉淀成的"答题套路" | `user_memories(category=method)` | 只在面试与复盘场景 |
| L3 检索 | 历史对话 / 笔记 / 复盘的原文 | `search_documents`（MySQL 全文索引 + ngram） | 只在你话里出现回溯指代时才查 |

关键设计：

- **来源加权**：行为证据（答题/面试表现）> 自述与简历 > 模型推断；**弱来源不能覆盖强来源**，
  同权重证据做加权平均并累加证据次数。
- **容量上限 + 自动整合**：每类有上限，超限触发一次模型整合（合并相近、淘汰最不重要的），
  避免画像无限膨胀、也控制提示词预算。
- **先确认再写入**：模型推断出的画像落成"待确认"，用户确认后才参与注入。
- **可解释可删**：每次变更写日志，用户能在"我的画像"里查看、修改、删除。
- **按用户隔离**：所有读写都按 `user_id` 过滤，写测试时用**遍历所有带 user_id 的表的泛化断言**兜底。

### 2）模式路由：把"功能分支"变成一张注册表

`select_model`（0 快速回答 / 1 知识精讲 / 2 刷题评测 / 3 简历优化 / 4 模拟面试 / 5 面试复盘）
映射到 `(agent_name, scene, label)`。好处：新增模式只加一行；前后端只用一个数字对齐；
未知取值有明确回退；不同场景可以绑定不同的提示词模板与注入规则。

### 3）成本可观测：把 token 计量做进唯一的模型出口

一次用户提问可能触发**多次模型调用**（会话摘要压缩、画像抽取、记忆合并……），
所以按"接口次数"限流和真实花销不是一回事。做法是在唯一的模型出口
（`get_chat_model`）挂 LangChain callback，从 provider 返回的 `usage_metadata` 记账，
并落了 `usage_records` 明细表；配额与全局熔断都基于它。

**实测坑**：流式响应的用量**不在最后一帧**（读最后一块会拿到 `None`，配额就静默失效）；
且**推理 token 计费且常占大头**（实测一次输出 137 token 里 133 是 reasoning），
所以按 `total_tokens` 统计而不是正文。

### 4）从"能跑"到"敢给人用"的工程化

多环境（`development` / `demo` / `test` / `production`）配置分层：环境名写错**启动即失败**；
演示环境有**按 IP 的配额、全局日预算熔断、单场面试时长上限、降本开关**，
配额配置是 JSON 文件**热重载**（最多 5 秒生效）。

部署侧踩过并修掉的真实问题（面试聊"你遇到过什么坑"时很有料）：

- **反代下的客户端 IP**：`X-Forwarded-For` 取错位置（可伪造）、nginx realip 的信任网段、
  上游把真实 IP 追加在末尾……最后用"上游追加 + 下游按对端校验"的方式把 IP 传对。
- **Nginx 缓存上游 IP**：只重建后端时 nginx 仍打旧 IP → 持续 502；用 `resolver` + 变量化 `proxy_pass` 解决。
- **SSE 被代理缓冲**：不关 `proxy_buffering` 时打字机效果变成"憋一大段再一次性出现"。
- **跨架构构建**：在 Apple Silicon 上交叉构建 amd64 镜像时 `uv` 在 QEMU 下段错误，
  最终改成"在服务器上构建"，并加了 `docker image inspect` 的架构自检。
- **`docker load` 会覆盖同名标签**：离线传镜像时把第三方镜像也打进去，把服务器上正确架构的镜像静默换掉了。

> 这些不是"配置清单"，而是**验证环境与目标环境不一致时踩出来的**——
> 所以后来养成了一个习惯：**每个结论都留一条能复现的命令**（冒烟脚本、架构自检、配额查询 SQL）。
