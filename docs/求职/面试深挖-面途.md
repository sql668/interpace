## 一、整体架构与模式路由

### Q1. 你这个项目的"模式"是怎么路由的？为什么不做成一堆 if-else？

**考点**：抽象能力、可扩展性、"配置 vs 代码"的判断。

**高分回答**：

前端只提交一个 `select_model` 数字（0 快速回答 / 1 知识精讲 / 2 刷题评测 / 3 简历优化 /
4 模拟面试 / 5 面试复盘），后端有一张**注册表**把它映射成 `(agent_name, scene, label)`。

抽成注册表有三个具体收益：

1. **新增模式不改业务代码**：加一行配置，链路自动适配（提示词模板、注入规则、落库场景）；
2. **前后端契约只有一个数字**：避免 `"interview"` / `"mock_interview"` 这类字符串在两边漂移；
3. **支持"同场景不同模式"**：知识精讲在学习室和面试间共用一个 `scene`，靠会话的
   `session_model` 区分——写死在 if-else 里这种复用会很难看。

另外**未知取值回退到默认模式，而不是报错**：`select_model` 是历史数据里的事实，
枚举变化不该让老会话打不开。

**代码依据**：`interpace-backend/app/agent/scene_registry.py`

```python
# scene_registry.py:40-47  注册表本体
SCENE_SPECS: dict[int, SceneSpec] = {
    0: DEFAULT_SCENE_SPEC,
    1: SceneSpec(1, "difficulty_learner", "study", "知识精讲"),
    2: SceneSpec(2, "quiz_generate_workflow", "quiz", "刷题评测"),
    3: SceneSpec(3, "resume_parser", "resume", "简历优化"),
    4: SceneSpec(4, "interview_host", "interview", "模拟面试"),
    5: SceneSpec(5, "interview_evaluator", "evaluation", "面试复盘"),
}

# scene_registry.py:56-58  未知取值回退（刻意不报错）
if select_model is None:
    return DEFAULT_SCENE_SPEC
return SCENE_SPECS.get(select_model, DEFAULT_SCENE_SPEC)
```

调用点只有一处：`app/services/stream_chat_service.py` 里 `resolve_scene(select_model)`
拿到 `(agent_name, scene)`，后续链路全按它们走。

**追问**：

1. *为什么用数字而不是字符串 scene？* —— 它同时是数据库列（`chat_messages.select_model`），
   数字占空间小、便于前端做 tab 索引；代价是可读性差，所以注册表里配了 `label`。
2. *要让用户自定义模式，你要改什么？* —— 场景注册表落库（可增删）、提示词模板可由用户维护、
   再加配额与权限（自定义模式可能意味着更多模型调用）、前端从接口拉模式列表。
3. *两个房间共用 `select_model=1`，怎么保证不串？* —— 所有接口都带 `session_model` 做归属校验
   （会话存在 + 属于当前用户 + 类型匹配，否则 404）。

**红旗**：只答"这样代码好看"，说不出具体收益。

### Q2. 一次提问从浏览器到模型，中间经过哪些环节？为什么这么排？

**考点**：端到端理解、分层意识、能否讲清关键约束。

**高分回答**：

```
浏览器 → (Vite 代理 / Nginx) → POST /api/v1/sessions/{id}/stream-chat
  1) 鉴权（Bearer Token）
  2) 会话归属校验（存在 + 属于当前用户 + session_model 匹配）
  3) 解析执行模式（select_model → agent / scene）
  4) 解析附件（文档取正文、图片取字节，组装成多模态内容块）
  5) 预写一条消息占位行并提交 —— 为了拿到 row.id
  6) 组装提示词：模板 + 画像/记忆注入 + 会话摘要 + 最近历史 + 本轮输入
  7) LangGraph 执行（当前是单节点图：提示词 → 模型）
  8) 模型流式输出 → 转成 SSE 的 delta 事件推给前端
  9) 结束后落库（正文、状态、附件段、关联的题库/面试/画像提案 id）
 10) 后置处理：按场景落面试记录 / 出题结果 / 画像待确认
```

两个"顺序不能换"的点：

- **第 5 步必须在第 6 步之前**：组装提示词要用 `current_message_id` 做历史截断（只取它之前的历史），
  停止功能要登记 `message_id`，前端还要靠它把气泡挂上界面。
- **第 4 步要在第 5 步之前**：附件解析出的文本要写进消息行留档，否则刷新后看不到"这条消息带了什么"。

**代码依据**：`interpace-backend/app/services/stream_chat_service.py` 的
`StreamChatService.stream_chat()`——函数体里每一步都有编号注释：

```python
# 1) 会话归属校验，不存在则抛 404。
# 2) 解析执行模式：spec = resolve_scene(select_model)
# 3) 解析附件内容：AttachmentContentService.resolve(...)
# 4) 预写入消息占位行：db.add(row); db.commit(); db.refresh(row)   ← 为了拿到 row.id
# 5) 构建个性化提示词（注入用户画像）；无模板时返回 None 由链路层兜底
# 6) 组装编排图（历史截断 + LLM 绑定 + 输入变量准备）
#    def event_generator(): ...  ← SSE 的 start / delta / error / done 都在这
```

SSE 事件的构造集中在 `_sse_data(...)`（`data: {json}\n\n`，没有 `event:` 字段，
前端按 `type` 分发）。

**追问**：

1. *为什么不"先返回内容再落库"？* —— 停止或断开时会丢数据；先落占位行，即使中途失败也有可追溯记录。
2. *SSE 有哪些事件？* —— `start`（带 `message_id`）、`delta`（正文增量）、`error`、
   `done`（完整正文 + `stopped` + 关联的 `quiz_paper_id` / `interview_id` / `profile_proposal_id`）。
   **`done` 一定出现且是最后一帧**，前端据此收尾。
3. *模型中途报错呢？* —— 已生成的部分照常落库，先发 `error` 事件再发 `done`，保证前端状态机能收敛。

### Q3. 你怎么保证"一次提问触发的多次模型调用"不会把成本吃爆？

**考点**：成本意识、对调用链的掌握程度（这题能区分"做过"和"只是跑通过"）。

**高分回答**：

先摆出放大点——一次用户提问背后可能不止一次模型调用：

| 放大点 | 触发条件 |
| --- | --- |
| 会话摘要压缩 | 更早的历史攒够一批就压一次（增量） |
| 简历画像抽取 | 简历场景每轮额外一次 |
| 记忆抽取 / 整合 | 评分、复盘之后 |
| 出题 / 评分 / 复盘 | 各自独立的一次调用 |

三层防护：

1. **计量收口**：所有调用都经过唯一出口 `get_chat_model`，在那里挂 LangChain callback
   把真实用量写进 `usage_records`（"流式也能拿到用量"见 Q20）；
2. **配额**：按 IP 的场景次数（对话/出题/复盘）+ 按 IP 的累计 token + **全局日预算熔断**。
   全局那层是关键——按用户限流挡不住"很多人各用一点"的长尾；
3. **降本开关**：演示环境关掉用户看不见的后台调用（画像抽取、记忆抽取与合并、摘要压缩），
   并压低单次输出上限。

**追问**：

1. *关掉后台抽取会损失什么？* —— 记忆不再自动更新，"越用越好用"退化成"不记得你"。
   这是**演示环境的取舍**：先保证不烧钱、主链路完整，正式环境再打开。
2. *怎么判断该关哪个？* —— 看 `usage_records` 按 scene 分组的花销占比。
   实测一次复盘约 3.1k token，一轮普通对话几百到 1.5k——**复盘与出题是大头，对话轮数再多也不是最贵的**。

**代码依据**：

```python
# app/services/usage_quota_service.py:216-218  检查顺序写进了 docstring（可解释性）
"""检查顺序是刻意从"最容易解释"到"最细"：全局熔断 → 单 IP 累计上限 →
单 IP 当日次数。这样用户看到的拒绝理由是最外层的那条……"""

# app/services/usage_quota_service.py:228-241  全局熔断（护住钱包的那层）
if (global_usage.tokens_today >= limits.global_limits.daily_token_budget
        or global_usage.calls_today >= limits.global_limits.daily_call_budget):
    UsageQuotaService._reject(reason="global_budget", detail={...}, message=...)

# app/agent/llm.py:73-74  检查在建模型之前
# 配额检查放在**建模型之前**：超额时连实例都不创建，直接 429。
UsageQuotaService.check_before_call(scene=scene, client_ip=client_ip)
```

## 二、三层长期记忆（重点）

### Q4. 为什么记忆要分三层？一层画像不够吗？

**考点**：架构判断力——能否说清"分层的依据"，而不是"我分了三层"。

**高分回答**：

分层的依据是**生命周期与访问模式不同**，不是"信息种类不同"：

| 层 | 写入频率 | 读取方式 | 约束 |
| --- | --- | --- | --- |
| L1 明细 | 高频（每次评分 / 复盘 / 确认） | 按场景与岗位过滤后**挑选**注入 | 容量有上限 |
| L2 方法 | 低频（同类问题反复出现才沉淀） | 只在面试 / 复盘场景注入 | 要求**语义稳定**（同类复用同一条） |
| L3 检索 | 每次产出内容都写索引 | **按关键词检索**，返回原文 | 量大，不能常驻提示词 |

只做一层会同时踩两个坑：

- 想覆盖 L3 的能力（翻出你三个月前说过的原话），画像会膨胀到无法常驻提示词；
- 想覆盖 L1/L2 的差异（"这条是技能熟练度" vs "这条是答题套路"），只能靠字符串约定，
  下次要按类别注入时又得重新解析。

**代码依据**：三层的"分界线"其实写在**注入规则**里，而不是表结构里——

```python
# app/services/user_profile_service.py:21-33  注入规则（L1/L2 的分界在这里）
class InjectionRule:
    """画像会长（技能到 30 条、薄弱点 50 条），**无差别全塞进去会把
    真正重要的信息稀释掉**……不同场景关心的东西本来就不一样：
    面试看岗位与经验深度，刷题看技能与薄弱点，所以按场景给不同的条数上限与关注点。"""
    max_skills: int
    max_weak_topics: int
    focus: str
    # 是否注入 L2 的答题方法条目（T9.12）。只在对「怎么答」有意义的场景打开：
    # 模拟面试与面试复盘；知识精讲是讲知识点的地方，不注入。

# app/db/models.py:686-692  L3 的存储（独立表 + 全文索引）
Index("ft_search_documents_content", "title", "content",
      mysql_prefix="FULLTEXT", mysql_with_parser="ngram")

# app/db/models.py:564 起  L1/L2 同在 user_memories，靠 category 区分
category: Mapped[int]  # 0=技能 1=薄弱点 2=答题方法
```

**追问**：

1. *只保留两层，砍哪层？* —— 砍 L2：方法本质是"L1 里某一类的聚合视图"，可由明细推导
   （代价是每次注入都要现场聚合，语义稳定性变差）。L1 与 L3 都不能砍：一个是结论，一个是证据来源。
2. *L1 和 L2 在同一张表（`user_memories`），凭什么算两层？* —— 靠 `category` 区分，
   但**分层的价值体现在注入规则**：L2 只在面试/复盘注入（`InjectionRule.include_methods`），
   L1 是全场景按需挑。同表不同策略，这就是分层。
3. *L3 存对话全文会不会太重？* —— 存原文但**不常驻提示词**，只在检索命中时取有限长度
   （当前限 500 字）注入；索引表按 `(user_id, source_type)` 建索引。

### Q5. 记忆冲突了怎么办？模型说"他会 Java"，但行为证据显示他 Java 题做得很差。

**考点**：合并策略是否真的实现过（最容易露馅的一题）。

**高分回答**：

先明确来源权重，这是整套设计的地基：

```
行为证据（答题、面试表现）  weight = 3
自述 / 简历                weight = 2
模型推断                   weight = 1
```

冲突处理：

1. **弱来源不能覆盖强来源**：模型推断（1）推翻不了行为证据（3）；
2. **强来源可以纠正弱来源**：连续几次 Java 题答得好 → 覆盖"自述不熟 Java"；
3. **同权重证据做加权平均**，累加 `evidence_count`、更新 `last_evidence_at`；
4. 两者都强但长期背离时，**交给用户裁决**——这正是"待确认"机制的意义。

本质区别要讲出来：**行为证据可重复、可累积，自述是一次性声明**。
所以"以最新一条为准"在这里是错的：用户今天随口说一句"我不太会 Java"，
不该抹掉三个月的行为证据。

**代码依据**：`interpace-backend/app/services/user_memory_service.py`

```python
# user_memory_service.py:39-41  来源权重就是三个常量
SOURCE_SELF_REPORT = 1   # 用户自述
SOURCE_BEHAVIOR    = 3   # 行为证据（刷题得分、面试表现）  ← 推测值 2 是简历

# user_memory_service.py:492-494  待确认只针对"模型推断"，其余直接生效（D20）
need_approval = (
    source == SOURCE_INFERENCE if pending_approval is None else pending_approval
)

# user_memory_service.py:357-363  合并的入口是"同名同类别先查再合并"，
# 所以重复证据不会产生多条，而是走 upsert_memory 的加权合并分支
existing = db.scalar(select(UserMemory).where(
    UserMemory.user_id == user_id,
    UserMemory.category == category,
    UserMemory.name == text,
))
```

**追问**：

1. *那自述什么时候该生效？* —— 当它改变的是"目标"而不是"能力"（求职意向、目标岗位），
   那属于 `user_profiles` 的意图字段，是另一套写入路径，与能力记忆分开。
2. *用户坚持要改呢？* —— 他在"我的画像"里手动改/删，来源记为自述；
   但对强于它的行为证据只降权不删除，避免误操作丢掉历史。
3. *待确认会不会很烦？* —— 只在**模型推断**这类低置信来源上要求确认；
   行为证据（答题、面试）直接写入，因为那是用户自己产生的。

### Q6. 掌握度怎么算？会不会越用越飘？

**考点**：数值设计、是否考虑置信度与衰减。

**高分回答**：

`mastery` 是 0~100 的整数，合并时按**来源权重加权平均**，不是直接覆盖：

```
new = (old * old_weight + evidence * new_weight) / (old_weight + new_weight)
```

配套字段：

- `confidence`：样本少时低 → **注入时降权**，避免"只答过一次就当成专家"；
- `evidence_count`：证据次数，判断结论是否稳固；
- `last_evidence_at`：最后一次证据时间，**给将来的时间衰减留的**。

**诚实项**：目前是"加权平均 + 证据计数"，**时间衰减还没做**——半年没碰的技能，
掌握度还是当时的值。改进方向是按半衰期衰减 `confidence`（而不是 `mastery`），
让"生疏"体现为"不确定"，而不是"能力退步"。

**代码依据**：`user_memories` 表把"值"和"可信度"分开存——这是能谈衰减的前提：

```python
# app/db/models.py   user_memories 的字段
mastery: Mapped[int]           # 掌握度 0-100（值）
confidence: Mapped[int]        # 置信度 0-100（这个值的可信程度）← 衰减该打在这里
evidence_count: Mapped[int]    # 被证据命中过几次
last_evidence_at: Mapped[int | None]  # 最后一次证据时间 ← 时间衰减的输入
source: Mapped[int]            # 来源权重（1/2/3）
```

**追问**：

1. *为什么不取最近 N 次平均？* —— 受偶发影响大：一次网络卡顿式的低分能把分数拉垮；
   加权平均 + 证据计数更稳。
2. *连续答对 5 次再错 1 次，分数怎么变？* —— 有证据计数在，第 6 次只占小权重、分数微降；
   如果这是第 2 次证据，就会明显下降。这就是"早期敏感、后期稳健"。

### Q7. 容量上限触发的"自动整合"具体怎么做的？会不会把用户细节弄丢？

**考点**：LangGraph 的实际用法 + 数据安全。

**高分回答**：

记忆写入走的是 LangGraph **状态图**，不是一段串行函数：

```
extract（抽取候选）→ validate（校验/归一）→ persist（落库）
                                              ↓ 某类超过上限
                                       consolidate（整合）→ persist
```

`persist` 节点发现某类超限时置位 `needs_consolidation`，**条件边**把流程导到整合节点：
把该类**全部现有条目**交给模型，要求"合并相近、淘汰最不重要的，输出最终保留清单 + 要淘汰的条目名"，
再落库。

用状态图而不是 if-else：分支显式（哪一步触发整合看得见）、每个节点可单独打点观测、
后续加节点（比如冲突检测）不用重写控制流。

防丢失：整合前把被改动条目的 `before_json` 写进 `user_memory_logs` 变更日志，用户可追溯；
只淘汰**低权重 + 低证据次数**的条目；被淘汰的原始事实仍在 L3 索引里，需要时能检索回来。

**代码依据**：`interpace-backend/app/services/memory_extract_service.py`（LangGraph 组装）

```python
# memory_extract_service.py:420-435  状态图的节点与边，条件边就是"超限才整合"
graph.add_node("extract", extract_node)
graph.add_node("validate", validate_node)
graph.add_node("capacity", capacity_node)
graph.add_node("consolidate", consolidate_node)
graph.add_node("persist", persist_node)
graph.add_edge(START, "extract")
graph.add_edge("extract", "validate")
graph.add_edge("validate", "capacity")
# 超限就先整合一次再落库；否则直接落库
```

### Q8. L3 为什么用 MySQL 全文索引而不是向量库？中文怎么处理？

**考点**：选型判断力 + 是否踩过中文分词的坑（**极容易区分真假**）。

**高分回答**：

**约束驱动**：目标环境 2 核 2G。向量库单独跑就是几百 MB 常驻内存，还要额外一次 embedding 调用
（延迟 + 成本），对"单机演示"不划算。而 MySQL 全文检索能覆盖当前需求：
**关键词召回 + 返回原文**。

**中文必须用 ngram 分词器**：

```sql
FULLTEXT INDEX ... WITH PARSER ngram
```

InnoDB 默认按空格与标点切词，中文整句会被当成**一个词**——结果是"能建索引、能查询、
就是搜不到"，属于**静默失效**（实测踩过）。

两个实践细节：

- 索引**有可见性延迟**：刚写入的行可能立刻搜不到（真机验证过），
  所以别用"写完立刻搜"来断言功能正常；
- 逐词匹配做不到语义召回（搜"缓存穿透"匹配不到"缓存击穿"）。

**什么时候换向量检索**：需要语义召回、跨措辞、规模十万级以上、内存预算允许时。
迁移路径是保留 `search_documents` 作为原文源，另建向量索引做混合排序（BM25 + 向量）。

**代码依据**：

```python
# app/db/models.py:686-692  中文检索的关键就这一行 mysql_with_parser="ngram"
Index("ft_search_documents_content", "title", "content",
      mysql_prefix="FULLTEXT",
      mysql_with_parser="ngram")

# app/db/models.py  表结构：原文单独存，便于"返回原文"而不是摘要
class SearchDocument(Base):
    __tablename__ = "search_documents"
    # user_id / source_type(0对话 1笔记 2复盘) / source_id / title / content(原文)
    # 唯一键 (user_id, source_type, source_id)：同一来源只索引一次，写时覆盖
```

这条索引在**迁移文件**里也带着解析器（`alembic/versions/598c8ac58d95_baseline_schema.py`），
所以新环境不会漏配——autogenerate 容易把这个参数丢掉，基线是人工核对过的。

**追问**：

1. *ngram 的 token size 怎么选？* —— 默认 2（2 字窗口）。中文两字词最常见；
   取 1 索引爆炸、取 3 漏掉两字关键词。代价是索引体积变大。
2. *为什么检索结果返回原文而不是摘要？* —— 回溯时用户想听的是"我当时怎么说的"，
   摘要会二次失真；而且原文更省钱（不用再调模型）。

### Q9. 记忆什么时候注入？每次都注入吗？token 预算怎么控？

**考点**：提示词工程 + 成本控制。

**高分回答**：

按层、按场景、按需注入：

| 层 | 注入条件 |
| --- | --- |
| L1 | 每次回答前，**按当前场景与岗位过滤后挑相关条目**（不是全量） |
| L2 | 只在 `interview` / `evaluation` 场景（`InjectionRule.include_methods`） |
| L3 | **只在检测到"回溯指代"时才检索**，且注入限长 500 字 |

为什么 L3 要按需：每次都检索注入等于每轮输入多一段原文，成本翻倍，
还可能把不相关内容塞进上下文干扰模型。

"回溯指代"现在用**关键词 + 句式**判定（"上次 / 之前 / 那个方案 / 我们聊过的"）。
更稳的是加一次极小的分类调用或规则+小模型混合，但那本身也是成本，要权衡。

**代码依据**：`interpace-backend/app/agent/memory.py`

```python
# memory.py:29-40  触发 L3 检索的关键词（"回溯指代"）
RECALL_KEYWORDS = ("之前", "上次", "上回", "刚刚", "刚才", "前面",
                   "以前", "历史", "聊过", "说过", "提过", ...)

# memory.py:52  注入限长——不常驻提示词，命中才取有限长度
RECALL_SNIPPET_MAX_CHARS = 500

# memory.py:72  判定函数
def should_recall(text: str) -> bool:
    return any(keyword in text for keyword in RECALL_KEYWORDS)
```

调用点在 `app/agent/prompt_layer.py` 组装提示词时：
`if should_recall(request_text): memory_context = build_memory_context(...)`——
**只有命中才查库**，这就是"每轮不检索"的落地处。

**追问**：

1. *判断错了漏检索会怎样？* —— 模型答"我不记得"，体验受损但不出错，
   所以关键词表偏宽松（宁可多检索一点）。
2. *怎么知道注入的内容有用？* —— 注入内容全部落日志（可解释），
   再加离线评测：构造"同一用户多轮轨迹"，检查第 N 轮回答是否引用了前面的事实。
3. *注入会不会带来隐私问题？* —— L1/L2/L3 读写**全部按 `user_id` 过滤**；
   测试里有"拿别人的 id 改/删/批准一律 404"和"遍历所有带 `user_id` 的表"的泛化断言。

### Q10. 你怎么评测记忆系统？凭什么说它"越用越好用"？

**考点**：有没有评测意识——**最能区分"做了功能"和"做了系统"的一题**。

**高分回答**：

分三层评测，并说清哪层做了、哪层只是设计：

1. **规则与隔离（已做，含在 251 个后端用例里）**：来源权重合并、弱不覆盖强、

2. **行为评测（设计好未实现）**：构造"同一用户多轮轨迹"（第 1 轮说项目用了 Redis，
   第 5 轮问"上次那个缓存方案"），断言注入内容包含关键实体；

3. **效果评测（未做）**：注入前/后的回答质量 A/B 盲评（人工或裁判模型），
   看用户是否真的感到"被记住"。

**诚实项**：1 完整，2、3 只有设计。这是我认为下一步最该补的地方——
否则"越用越好用"只是产品愿望，没有证据。

**代码依据**：隔离与级联清理不是"抽查某张表"，而是**泛化断言**——
遍历 metadata 里所有带 `user_id` 的表，任何一张有残留就失败。
这样"以后加了新表却忘了改删除逻辑"会被自动抓到（这个坑在本项目真踩过五次）：

```python

leftover: list[str] = []
for table in Base.metadata.sorted_tables:
    if "user_id" not in table.columns or table.name in CASCADE_EXEMPT_TABLES:
        continue
    remaining = db.execute(table.select().where(table.c.user_id == user_id)).first()
    if remaining is not None:
        leftover.append(table.name)
assert not leftover, f"删除用户后这些表还有残留数据: {leftover}"
```

**为什么 `usage_records` 是唯一例外**：它是**账本**，删账号时**刻意保留**——
否则"删号重建"就能把按 IP 的累计额度洗回来，配额就白做了。这条例外在代码里有注释，不是遗漏。

**追问**：

1. *记忆被污染了（错误记忆被注入）怎么发现与回滚？* —— 变更日志定位来源；
   用户在"我的画像"里能删；注入内容有日志能回溯"为什么这轮答歪了"；
   极端情况可按来源类型批量清理（比如清掉全部模型推断条目）。

### Q11. 刷题为什么设计成"先确认参数再出题"？

**考点**：对模型行为的理解 + 产品化思维。

**高分回答**：

参数不全时模型会**自己假设**（岗位、难度、题量），假设错就出一整套偏题，
白白浪费一次完整调用。所以模板里写死了"**在用户明确确认之前，绝对不要输出题目**"，
并要求先把三项复述清楚请用户确认。

代价是多一轮交互——用户说"出 5 道题"，通常还要再确认一次。换来的是出题准确率。

**代码依据**：提示词模板里那句硬约束（`app/services/prompt_template_seed_service.py:144`）

```python
QUIZ_GENERATE_TEMPLATE = """当前模式：刷题评测。

## 第一步：确认参数（这一步不要出题）
把下面三项复述清楚请用户确认：目标岗位 / 难度（初级·中级·高级）/ 题量
…
**在用户明确确认之前，绝对不要输出题目。**

## 第二步：用户确认后出题
用户确认后，直接输出**一个 JSON 对象**，不要任何解释、前后缀，也不要用 Markdown 代码块包裹。
硬性要求：
- questions 的条数必须与 question_count 一致
- 每道题的 question 与 reference_answer 都不能为空
"""
```

模板是**可版本化**的（`prompt_templates` 表带 `version` / `is_active`，配套回滚接口），
改提示词不用改代码、也能一键回滚——这是"提示词也是资产"的落地方式。

**追问**：

1. *怎么降低这一轮的成本？* —— 从上下文能推断出参数时，用一句话合并确认
   （"我按后端中级 5 道出题，可以吗"），而不是逐项问。
2. *用户说"别问了直接出"呢？* —— 模板里给一条例外：用户显式表达不需要确认时按缺省参数直接出，
   并在题目卡片上标明用了哪些假设。

### Q12. 出题结果解析失败怎么办？现在怎么处理的，你觉得够吗？

**考点**：对 LLM 输出不可靠的处理、容错设计的成熟度。

**高分回答**：

模板强约束输出"**一个 JSON 对象、不要解释、不要代码块**"；解析器还做了代码块剥离与字段归一
（题量必须与 `question_count` 一致、题干不能为空）。

解析失败时**静默跳过**：不落库、不渲染卡片。

**诚实项**：这个"静默"是缺陷——用户会觉得"我确认了但卡片没出来"，
而且没有任何提示。改进方向有两条：

1. 解析失败时显式回一条消息（"这次出题没成功，换个说法再试"）；
2. 把失败率做成指标（解析失败次数 / 出题总次数），否则这类问题只在用户抱怨时才知道。

**追问**：

1. *为什么不用 function calling / structured output？* —— 当前走的是 OpenAI 兼容接口，
   不同模型对结构化输出的支持不一致；用提示词约束 + 解析容错的可移植性更好。
   如果上游稳定支持，应该优先用结构化输出，能省掉一层容错。
2. *模型偶尔加解释，能不能用正则兜？* —— 已经做了"取第一个 `{...}` 子串"的兜底，
   但不能过度依赖：正则无法处理嵌套与转义，最后还是要靠"约束输出 + 失败可观测"。

**代码依据**：解析器在 `app/services/quiz_service.py`，两层容错一目了然：

### Q13. 一份卷子只评分一次，为什么？重复提交返回 409 合理吗？

**考点**：幂等与状态机的取舍。

**高分回答**：

两个理由：

1. **总分要稳定**：同一份卷子多次评分会因为模型波动给出不同分数，用户会困惑"到底几分"；
2. **避免重复计费**：评分是一次完整模型调用。

409（Conflict）比 400 更准确：请求本身合法，是与"当前状态"冲突。

**追问**：

1. *评分过程中模型超时或失败，用户答案会丢吗？* —— 不会：流程是**先落用户答案并置
   `status=已提交`，再调模型评分**，评分失败可以重试（重试时不会丢答案）。
2. *这个设计对前端有什么要求？* —— 必须有"重试评分"的入口，
   否则一次失败这份卷子就废了。
3. *如果要做"重新评分"功能怎么改？* —— 允许覆盖但明确提示"会替换已有评分"，
   并把旧结果存进历史表（append-only），而不是静默覆盖。

**代码依据**：`interpace-backend/app/services/quiz_evaluation_service.py`

```python

# :97-108  第 1 步：先把答案落库并 commit —— 外部调用失败也不能丢用户数据
# 1) 先把用户作答写进题目行并提交：评分是外部调用，失败概率不为零，
#    用户的答案不能跟着评分一起丢。
paper.status = QUIZ_STATUS_SUBMITTED
db.add(paper); db.commit()

# :113-120  第 2 步：调模型评分（失败抛 502，答案已保住，可空 answers 重试）
# :122-143  第 3 步：评分写回 + 画像写回放同一个事务
#    两件事放在同一个事务里提交：要么都成功，要么都回滚——
#    不会出现「卷子已评分但画像没更新、重试又被 409 挡住」的尴尬状态。
```

### Q14. 评分怎么回写画像？为什么回写"薄弱点"而不是"技能掌握度"？

**考点**：跨模块联动 + 数据语义的严谨性。

**高分回答**：

评分返回 `weak_topics` → 通过统一的记忆写入入口（`UserMemoryService.ingest`）写入 L1，
**来源标记为行为证据（最高权重）**，并累加证据次数、更新掌握度。

只写薄弱点、不直接推断"技能掌握度"，是因为**一次测验的样本量太小**：
你这轮答对了不代表掌握，答错了也可能只是没睡好。标薄弱点更保守——
它的作用是"下次多关注"，而不是"给你下结论"。

**追问**：

1. *重复测同一个知识点会怎样？* —— 证据累加 + 加权平均，不会产生多条重复条目
   （写入前先按同名合并）。
2. *之后答对了同一知识点呢？* —— 新证据（同为行为证据）与旧值加权平均，
   `evidence_count` 增加，掌握度回升。
3. *为什么所有写入都要过一个统一入口？* —— 合并规则、来源权重、容量检查、变更日志
   只写一遍；散在各模块里迟早出现"某条路忘了记证据次数"这类不一致。

**代码依据**：只回写 `weak_topics`，来源标记为行为证据，且**不跑二次抽取**。

## 四、面试间：简历优化 + 模拟面试 + 复盘

### Q15. 面试记录为什么用 JSON 列（`qa_object`）而不是问答子表？

**考点**：建模取舍，能不能讲清"什么时候该拆表"。

**高分回答**：

面试问答是**整体读写**的：一场面试一次性读取，按轮追加。查询需求弱（不需要"按某道题做聚合"），
所以用 JSON 列：一次更新追加一轮、事务小、不用维护子表外键与顺序。

代价也要说清楚：**无法按题目做 SQL 聚合、单条问答无法建索引**，
JSON 列原地修改不会被 SQLAlchemy 识别（必须显式赋值 + `add`）。

**诚实项**：当时选择它还有时间点因素——`create_all` 不会给已有表加列，
拆子表意味着动表结构，而迁移能力当时还没就绪。**现在 Alembic 已经落地**，

### Q16. 面试时长怎么算？中途关掉页面会怎样？

**考点**：口径定义、边界情况处理。

**高分回答**：

时长 = `now - interview.created_at`，在 `finish` 时冻结（`finish` 幂等，重复调用只返回

**包含用户思考时间**——这是产品定义，不是技术限制（要"有效作答时长"就得按每轮问答的时间差累加）。

边界：用户中途关页面 → 记录仍是"进行中"，直到显式结束或下次继续答。

### Q19. 语音用 WebSocket、文字用 SSE，为什么不做成一套？

**考点**：协议选型与工程权衡。

**高分回答**：

- **语音**是**双向实时**：音频上行 + 音频下行，必须长连接双向传，WebSocket 合适；
- **文字**只需要服务端单向推 token，SSE 更简单（走 HTTP、代理配置少、
  断线语义清晰），没必要引入双向通道。

两者的线上配置差异（都踩过）：

| | 必须配 |
| --- | --- |
| SSE | nginx `proxy_buffering off`，否则打字机变"一次性出现" |
| WebSocket | `proxy_http_version 1.1` + 转发 `Upgrade`/`Connection`，否则握手被拒 |

**追问**：

1. *如果统一用 WebSocket 会怎样？* —— 鉴权要自己写（浏览器 WS 不能带自定义头，
   只能走查询参数或首帧鉴权）、重连与消息序号要自己管、还要处理心跳；
   收益是少一套协议。当前场景不值得。
2. *SSE 断线怎么处理？* —— 前端有 `AbortController` 可以主动中断；
   服务端的停止接口负责让后端停止生成；断开后已生成内容仍会落库，
   前端重新拉消息即可恢复。

**代码依据**：线上差异就写在 Nginx 的两段 `location` 里，一眼能对比出来。

### Q20. 流式对话的 token 用量怎么拿？为什么不能读最后一块？

**考点**：细节掌握程度（这题最能问出"真做过"还是"看过"）。

**高分回答**：

在唯一模型出口挂 LangChain callback，在 `on_llm_end` 里读 `usage_metadata`
（`input_tokens` / `output_tokens` / `total_tokens`，以及 `output_token_details.reasoning`）。

**关键坑**：流式响应里**带用量的那一帧不在末尾**（在中间某一帧）。
如果按"取 `chunks[-1]`"的写法会拿到 `None` → 记成 0 → **配额静默失效**
（不报错，只是永远拦不住）。所以必须用回调累积。

1. *拿不到用量怎么办？* —— 记 0 但**保留调用计数**，并打一条 warning 让它在日志里可见；
   否则 provider 哪天不返回用量，配额会悄悄退化成"只按次数"。
2. *为什么不能自己估算 token？* —— 中文场景按字符估算误差极大，
   而且**推理 token 根本估不出来**——实测一次输出 137 token 里 133 是 reasoning。

### Q21. 长会话上下文怎么控？为什么是"渐进式摘要"？

**考点**：上下文工程。

**高分回答**：

保留最近 10 条原文；更早的内容攒够 10 条压一次摘要，摘要注入提示词。
压缩是**增量**的：记录 `covered_message_id`，只压新增的那部分，不重压整段历史。

为什么不做两头的极端：

- **每轮都压**：成本高（每轮多一次模型调用），且反复压缩会丢细节；
- **直接截断**：早期关键信息（岗位、项目名、约定）会很早消失。

**追问**：

1. *摘要本身也可能丢关键信息，怎么兜？* —— L3 检索兜底：需要回溯时能翻出原文。
2. *摘要和长期记忆的分工？* —— 摘要 = 会话内的时序上下文（这次聊了什么）；
   记忆 = 跨会话的稳定事实（你是什么水平、你反复犯什么毛病）。
3. *为什么保留"最近 10 条"这个数字？* —— 经验值：足够覆盖当前话题的上下文，
   同时把输入 token 控制住；这个值应该做成可配置并按模型上下文窗口调整。

**代码依据**：两个常量 + 模块 docstring 就能概括整个策略。

```python

- 保留最近 `KEEP_RECENT` 条原文（细节不能丢）；
- 更早的消息攒够 `SUMMARY_TRIGGER` 条就压一次，把「上一版摘要 + 这一批新消息」一起压成新版；
- `covered_message_id` 记录压到哪条，据此算增量——所以长会话里大约每 10 条消息
```

### Q22. 为什么把配额做在"模型出口"，而不是接口入口？

### Q23. 2 核 2G 这个约束怎么影响了你的设计？

**考点**：约束驱动设计（很容易被追问到细节）。

**高分回答**：

| 约束 | 具体做法 |
| --- | --- |
| 内存紧 | 后端固定**单 uvicorn worker**（多 worker 只会互相抢内存） |
| 内存紧 | 不引入向量库 / embedding（同时省掉一次模型调用） |
| 内存紧 | MySQL 压 `innodb_buffer_pool_size`、关 `performance_schema`；Redis 设 `maxmemory` + LRU |
| 磁盘 | 所有容器日志加 `max-size` 轮转，否则磁盘会被日志吃满 |
| 构建 | 前端**不在服务器上构建**（vite 峰值约 1GB，容易和 MySQL 抢出 OOM） |
| 交付 | 多阶段镜像、非 root 运行、运行时镜像不带构建工具 |

实测：五个容器常驻内存约 **434MB**（MySQL 155M / 后端 189M / MinIO 74M / Redis 10M / Nginx 9M），
在 2G 机器上留出余量。

**追问**：

1. *用户量涨 10 倍，你先动哪里？* —— 先把 MySQL 拆出去（内存大头在自己机器上最危险），
   再考虑多实例 + Redis 做分布式限流/配额，前端与对象存储交给 CDN/对象存储服务。
2. *为什么现在不做多 worker？* —— 单机内存是瓶颈，多 worker 的收益（并发）远小于代价（内存），
   而且真正扛量要靠水平扩展而不是单机堆 worker。

**代码依据**：约束直接落到了编排文件与 Dockerfile 的参数上。

### Q24. 讲一个你排查最久的 bug。

**考点**：排查方法论（送分题也是送命题）。

**高分回答（挑"只在生产构建里出现"那个）**：

**现象**：开发模式一切正常，生产构建后打开聊天页报 `ReferenceError: Prism is not defined`。

**排查路径**：

1. 先在**真实构建产物**上复现（而不是读代码猜）——确认只有生产构建才炸；
2. 定位到报错来自打包后的某个 chunk，发现代码高亮的语言包引用的是**全局** `Prism`；
3. 再去看 Prism 核心：它挂全局的那句写成了
   `typeof global !== 'undefined' && (global.Prism = Prism)`——
   **浏览器里没有 `global`**（那是 Node 的东西），这句永远不执行；
4. 开发模式为什么正常？因为 Vite 的 CJS 互操作会补上 `global`。
   这也解释了"为什么只有生产构建才暴露"；
5. 修法两步：① 显式把 Prism 挂到 `globalThis`，并保证在语言包**之前**求值；
   ② 不把 prismjs 拆到独立 chunk（跨 chunk 的加载顺序不可控）。

**复盘出的结论**：`pnpm run build` 成功、开发模式正常，都**不代表生产产物没问题**。
所以后来加了"打开关键页面断言控制台无 error"这类检查项，并把"在真实产物上验证"写进了流程。

**追问**：

1. *再遇到"只在生产出现"的问题，你的第一步？* —— 在真实产物上复现 + 看控制台/网络，
   而不是读源码猜；差异一定来自"开发与生产的某个不同"（压缩、拆分、环境变量、polyfill）。
2. *怎么防止回归？* —— 把结论写进文档 + 关键路径加断言（这里是构建产物的控制台检查）。

**代码依据**：修复本身把"根因 + 为什么只有生产构建炸"写成了注释，永久留在代码里。

```ts

 * 浏览器里没有 `global`（那是 Node 的东西），所以**这句永远不执行**。

```

## 六、几个大概率的"综合题"

### Q25. 这个项目最难的地方是什么？

**高分回答**（挑真实难点，不要答"没遇到难的"）：

**最难的是"让记忆真正有用"而不是"存下来"**。存一条记忆很简单，难在这四件事同时成立：

1. **冲突不打架**：来源权重、弱不覆盖强；
2. **容量不爆炸**：超限自动整合，且整合不能幻觉出新东西；
3. **注入不浪费**：分层按需注入，token 预算可控；
4. **可解释可纠错**：用户能看见、能改、能删，出问题能定位到来源。

另外一个"难度被低估"的地方是**成本与体验的平衡**：把后台抽取全关掉最省钱，
但那就不叫"越用越好用"了；所以演示环境选择关掉、正式环境打开，
并把开关做成配置而不是代码分支。

**代码依据**：四个难点各自有明确的落点，面试时可以逐个翻。

### Q27. 这个项目你最大的收获是什么？

**高分回答**：

**"验证环境必须等于目标环境"**。这个项目里踩的坑几乎都源于这一点：
