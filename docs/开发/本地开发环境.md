# 本地开发环境的启动与停止

> 2026-09-30 实地核对过本机进程后写的，不是凭印象。

## 先分清两套环境（最容易搞混的地方）

同一台机器上**同时跑着两套**，端口、配置、数据全是分开的：

| | 本机开发栈（日常写代码用这个） | Docker 部署栈（验证部署用） |
| --- | --- | --- |
| 前端 | **5173**（Vite dev server，改代码热更新） | **8080**（容器里的 Nginx，跑的是构建产物） |
| 后端 | **8000**（uvicorn --reload） | 容器内 8000，只在容器网络里 |
| 后端环境 | `interpace-backend/.env.development`，`APP_ENV=development` | 根目录 `.env`，`APP_ENV=demo` |
| 配额 | **不生效** | 生效（按 IP 限 token / 轮数 / 复盘次数…） |
| MySQL | 本机原生安装的 MySQL 8 | 容器 `interpace-mysql`（自己的数据卷） |
| Redis / MinIO | **同一套**（本机 Docker 容器，两套共用） | |

> 所以：**写代码看 `localhost:5173`，验证部署看 `localhost:8080`**。
> 两边连的是**不同的数据库**——本机开发的数据在原生 MySQL 里，Docker 栈的数据在容器卷里。

## 本机开发栈的构成

| 组件 | 怎么跑的 | 端口 |
| --- | --- | --- |
| MySQL 8 | **本机原生安装**，有 launchd 自启配置（`/Library/LaunchDaemons/com.oracle.oss.mysql.mysqld.plist`） | 3306 |
| Redis | Docker 容器 `redis`（独立 compose 项目，`restart: always`） | 6379 |
| MinIO | Docker 容器 `minio`（独立 compose 项目，`restart: always`） | 9000 / 9001 |
| 后端 | `uv run uvicorn app.main:app --reload` | 8000 |
| 前端 | `pnpm run dev` | 5173 |

**三个中间件都是常驻的**（MySQL 开机自启，Redis/MinIO 是 `restart: always` 的容器），
平时不用管它们，除非要升级或改配置。

## 启动

### 指定用哪个环境

环境完全由 **`APP_ENV`** 决定，命令行传入的优先级最高（会覆盖配置文件里的值）：

```bash
./dev.sh start                 # 默认 development
APP_ENV=demo ./dev.sh start    # 用演示环境起（前提：interpace-backend/.env.demo 存在）
APP_ENV=production ./dev.sh start

# 不用脚本、手起也行（环境变量同样生效）
cd interpace-backend && APP_ENV=demo uv run uvicorn app.main:app --reload
```

环境名接受别名 `dev` / `prod` / `staging`；**写错会直接报错**（脚本和后端都会拦），
不会静默退回开发环境。

三个前提/限制：

1. **必须有对应的 `.env.{APP_ENV}` 文件**——配置只认这一个来源，没有基础 `.env` 兜底。
   `dev.sh` 会提前检查并告诉你缺哪个文件，不用等启动超时。
2. **`dev.sh` 同一时间只跑一个环境**（一套 PID 和端口）。已经在跑 development 时再执行
   `APP_ENV=demo ./dev.sh start`，它会明确拒绝并提示你先 `stop`。
3. 想**同时**看两个环境，就另起一个端口（见本文档"怎么在本地验证不同环境"的路径 A）。

`./dev.sh status` 会显示**当前运行的实例用的是哪个环境**（不是命令行指定的那个）：

```
后端  运行中  PID 93566  APP_ENV=development  http://127.0.0.1:8000
```

顺序无所谓（后端连不上库时启动会报错，但 --reload 会在你修好后再试），习惯上先确认中间件、再起后端、最后起前端。

```bash
# 1) 确认中间件在跑
nc -z -G 2 127.0.0.1 3306 && echo "MySQL 可连接"
#   注意别用 lsof 查 3306：mysqld 是以 _mysql 用户跑的，
#   不加 sudo 看不到它的监听端口，会误判成"没起"（实测踩过）。
docker ps --format '{{.Names}}\t{{.Status}}' | grep -E "^(redis|minio)\b"
curl -s -o /dev/null -w "MinIO: %{http_code}\n" http://127.0.0.1:9000/minio/health/live   # 期望 200

# 2) 后端（新开一个终端，保持前台运行）
cd interpace-backend
uv run uvicorn app.main:app --reload
# 看到 "Application startup complete" 就成了；http://127.0.0.1:8000/docs 是接口文档

# 3) 前端（再开一个终端）
cd interpace-frontend
pnpm run dev
# 打开 http://localhost:5173
```

**开发环境会自动建表**（`APP_ENV=development` 时跑 `create_all`），
所以新拉代码、改了模型，直接起服务就能用；**生产环境不会**（那边靠 Alembic 迁移）。

## 停止

```bash
# 后端 / 前端：在各自终端按 Ctrl+C 即可

# 中间件（一般不用停，它们是常驻的）
docker stop redis minio          # 停（下次 docker start redis minio）
docker restart redis minio       # 重启

# MySQL 是系统服务，别随手停（可能有别的项目在用）
sudo /usr/local/mysql/support-files/mysql.server stop
sudo /usr/local/mysql/support-files/mysql.server start
```

## 停掉中间件会怎样（了解降级行为）

| 停掉 | 表现 |
| --- | --- |
| Redis | **不影响主流程**：提示词模板缓存连不上会自动降级成"直接查库"（启动日志里会写明）。只是每次取模板多打一次数据库 |
| MinIO | **附件上传会失败**，其他功能（聊天、出题、面试、画像）都不走对象存储，正常 |
| MySQL | **整个后端起不来**（连接串是必填项，连不上就是启动失败） |

## 关键配置文件（别搞混）

| 文件 | 给谁用 | 内容要点 |
| --- | --- | --- |
| `interpace-backend/.env.development` | 本机后端 | `APP_ENV=development`、本机 MySQL 连接串（含 root 密码） |
| `interpace-frontend/.env.development` | 本机前端 | `VITE_API_BASE_URL=/api/v1`、代理目标 `http://127.0.0.1:8000` |
| 根目录 `.env` | **Docker compose** | `APP_ENV=demo`、容器内网地址（`mysql:3306`、`redis:6379`…） |

`.env` 相关文件都在 `.gitignore` 里，不会进仓库。

## 常用操作速查

```bash
# 后端测试（需要 MySQL 在跑）
cd interpace-backend && uv run pytest

# 前端构建（改了前端至少跑一次，能顺带发现类型错误）
cd interpace-frontend && pnpm run build

# 改数据库表结构（改完 models.py 必须配迁移）
cd interpace-backend && uv run alembic revision --autogenerate -m "说明"
# 详见 docs/开发/数据库变更流程.md
```

## 怎么在本地验证不同环境（开发 / 演示 / 测试 / 生产）

### 环境由 `APP_ENV` 决定，它影响四件事

| 影响 | 说明 |
| --- | --- |
| 读哪份配置 | `interpace-backend/.env.{APP_ENV}`。**没有"基础 .env 兜底"**——每套环境都必须有自己的文件，缺了就是启动报 `MYSQL_URL is required` |
| 建表方式 | `development` 会跑 `create_all` 补齐缺失的表；**其余环境都不跑**（生产靠 `alembic upgrade`） |
| 配额与降本开关 | 只有 `demo` 生效（`config/demo_limits.json` 里 `environments: ["demo"]`） |
| 日志级别 | 开发是 DEBUG，其余从 WARNING 起 |

> `APP_ENV` 写错（比如 `demoo`）会**启动即失败**并列出可选值——这是刻意的，
> 因为静默退回开发环境会让"配额以为开着、其实没开"。

### 最直接的验证办法：一个接口看全

后端有个专为这个场景准备的接口，把"当前环境 + 是否启用配额 + 配额数值 + 功能开关"全返回了：

```bash
curl -s http://127.0.0.1:8000/api/v1/config/runtime | python3 -m json.tool
```

```json
{
  "app_env": "demo",
  "quota_enforced": true,
  "features": { "voice_interview": false, "file_upload": true },
  "interview_max_minutes": 3,
  "limits": { "tokens_per_ip": 3000000, "turns_per_day": 10 }
}
```

**看 `app_env` 和 `quota_enforced` 两项就够了**，不用翻日志。

### 三种验证路径（按侵入性从小到大）

> 下面的**路径 A 与路径 C 都实测跑过**（2026-09-30）：同一台机器上同时跑
> 8000（development）和 8001（demo），两个 `/config/runtime` 的返回完全不同——
> 8001 是 `quota_enforced: true` + 完整 `limits`，8000 是 `false` + `limits: null`。

**路径 A：另起一个端口的后端（最快，不影响现有开发环境）**

> 用 `dev.sh` 也能直接指定环境：`APP_ENV=demo ./dev.sh start`。
> 但它只有一套 PID/端口，所以**同一时间只能跑一个环境**；要在开发环境照样跑着的
> 情况下再看一眼演示环境，就用下面这条"另起一个端口"的办法。

```bash
cd interpace-backend

# 1) 演示环境必须有 .env.demo（缺这个文件会启动失败）
cp .env.development .env.demo
#    改两处：APP_ENV=demo；MYSQL_URL 指向**独立库**（别用开发库）

# 2) 建库（演示环境用独立的库，放配额、清数据都不影响开发数据）
mysql -uroot -p'你的密码' -e \
  "CREATE DATABASE \`inter-pace-demo\` CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;"

# 3) 换个端口起（8000 上跑着开发环境，别挤掉它）
APP_ENV=demo uv run uvicorn app.main:app --port 8001

# 4) 验证
curl -s http://127.0.0.1:8001/api/v1/config/runtime | python3 -m json.tool
```

**路径 B：用 Docker 栈切环境（最接近真实部署）**

```bash
cd <项目根目录>
sed -i '' 's/^APP_ENV=.*/APP_ENV=demo/' .env      # 换成 demo / production / test
docker compose up -d backend
curl -s http://127.0.0.1:8080/api/v1/config/runtime | python3 -m json.tool
```

Docker 栈有自己的数据库（容器卷），**切环境不会污染本机开发的数据**，所以这条最适合验证"配置是否生效"。

**路径 C：验证"写错环境名会被拦住"**

```bash
cd interpace-backend
APP_ENV=demoo uv run uvicorn app.main:app --port 8002
# 期望：启动失败并提示可选值，而不是安静地按开发环境跑起来
```

### 各环境该看什么

| 环境 | 启动日志里的关键句 | `/config/runtime` 期望值 |
| --- | --- | --- |
| `development` | "开发环境：已用 create_all 补齐缺失的表" | `quota_enforced: false`、`limits: null` |
| `demo` | 无特殊句 | `quota_enforced: true`、`limits` 有值、`features` 反映降本开关 |
| `test` | 同 development | 同 development（当前配置里配额不对 test 生效） |
| `production` | "生产环境：跳过 create_all，表结构由 Alembic 迁移负责" | `quota_enforced: false` |

### 演示配额怎么验证"真的会拦"

光看 `quota_enforced: true` 不够，最好真触发一次：

1. 把 `config/demo_limits.json` 里某一项改小（例如 `turns_per_day: 1`），**最多 5 秒热生效**；
2. 在演示环境实例上发两轮对话；
3. 第二轮应收到 **429**，响应体里有 `detail.reason`（如 `ip_daily_quota`），前端会弹出后端那句中文提示；
4. 验完把数值改回去。

> 改容器里的 `/app/config/demo_limits.json` 是**临时**的——容器重建会被镜像里的原文件覆盖。
> 要持久改就改仓库里的 `interpace-backend/config/demo_limits.json` 再重建后端镜像。

### 前端的环境是"构建期"的

前端的 `VITE_*` 是**打包时**注入的，`pnpm run dev` 永远走 `.env.development`。
想看"生产构建的样子"：

```bash
cd interpace-frontend
pnpm run build && pnpm run preview
```

## 常见问题

| 现象 | 原因 / 处理 |
| --- | --- |
| 后端启动报连不上 MySQL | 本机 MySQL 没起：`sudo /usr/local/mysql/support-files/mysql.server start` |
| 5173 打不开、接口 404 | 后端没起，或起了但端口不是 8000（前端代理写死指向 127.0.0.1:8000） |
| 上传附件失败 | `docker ps` 看 `minio` 容器在不在 |
| 页面数据"不对" | 先确认你看的是 5173（本机开发）还是 8080（Docker 栈）——**两套数据是分开的** |
| 端口被占（8000/5173） | `lsof -nP -iTCP:8000 -sTCP:LISTEN` 找到占用进程（自己起的进程能查到）；Docker 栈用 8080，不冲突 |
| 查不到 MySQL 的监听端口 | 正常现象：`mysqld` 属于 `_mysql` 用户，不带 `sudo` 的 `lsof` 看不到。用 `nc -z 127.0.0.1 3306` 判断 |
