# 用户画像、长期记忆、用户与鉴权、提示词管理

对应后端 `app/routes/user_profile_routes.py`、`profile_proposal_routes.py`、
`user_routes.py`、`auth_routes.py`、`prompt_routes.py`。
通用约定见 [接口文档总览](./README.md)。下文路径省略 `/api/v1` 前缀。

## 画像与长期记忆的数据模型

用户画像由三部分拼成，`GET /profile` 一次返回：

| 部分 | 存储 | 说明 |
| --- | --- | --- |
| `intent` | `user_profiles` 的意图列 | 求职意向：目标岗位 / 年限 / 级别 |
| `target_skills` / `weak_topics` | `user_profiles` 的 JSON 列 | 由模型抽取 + 各模块回写的技能与薄弱点 |
| `memories` | `user_memories` 明细表 | 逐条能力记忆，带来源与置信度 |

`user_memories` 是本项目长期记忆的 L1 层（明细），字段语义：

| 字段 | 说明 |
| --- | --- |
| `category` | 0=技能，1=薄弱点，2=答题方法 |
| `mastery` | 掌握度 0~100 |
| `source` | 来源：3=行为证据 > 2=自述/简历 > 1=模型推断（**权重不同**） |
| `confidence` | 置信度 0~100 |
| `evidence_count` | 被证据命中的次数 |
| `pending_approval` | 1=待用户确认，未确认不参与注入 |

**记忆写入的合并规则**（长期记忆好不好用，全在这几条上）：

- 按来源权重比较：行为证据（答题 / 面试表现）**能覆盖**自述与模型推断，反之不行；
- 同权重来源的证据做加权平均，并累加 `evidence_count`；
- 每类有容量上限（技能 30 / 薄弱点 20 / 方法 20），超限抛
  `MemoryCapacityExceeded` 并转入记忆整合；
- 每次写入都记一条 `user_memory_logs` 变更日志（改了什么、改前改后）。

**用户之间完全隔离**：所有接口都按当前登录用户过滤，
拿别人的 `memory_id` 去改 / 删 / 批准 / 拒绝一律 404。

## GET `/profile`

```json
{
  "intent": { "target_job": "后端开发", "years_experience": "3", "target_level": "中级" },
  "target_skills": ["Python", "MySQL", "Redis"],
  "weak_topics": ["并发编程", "索引优化"],
  "memories": [
    { "id": 11, "category": 0, "category_label": "技能", "name": "Python",
      "mastery": 82, "mastery_label": "熟练", "source": 3, "source_label": "行为证据",
      "confidence": 90, "evidence_count": 4, "last_evidence_at": 1758000000,
      "pending_approval": 0, "updated_at": 1758000000 }
  ]
}
```

**没有画像记录时返回空结构**（`intent` 全为 `null`、三个数组为空），不是 404——
新用户打开"我的画像"页不该看到报错。

`memories` **包含待确认（`pending_approval=1`）的条目**，前端按该字段区分展示；
只有用户批准过的记忆才会参与后续的提示词注入。

## PUT `/profile`

只更新意图类字段，未传的字段保持原值：

```json
{ "target_job": "后端开发", "years_experience": "3", "target_level": "中级" }
```

## 记忆条目

### GET `/profile/memories`

查询参数 `category`（可选，0/1/2）过滤；不传返回全部。响应是**数组**（不是 `items` 包装）。

### POST `/profile/memories`

手动新增一条记忆，成功 **201**。

```json
{ "category": 0, "name": "Kubernetes", "mastery": 40 }
```

### PUT `/profile/memories/{memory_id}`

部分更新：`name` 与 `mastery` 都可省略。

### DELETE `/profile/memories/{memory_id}`

成功返回 **204 No Content**。

### GET `/profile/memories/pending`

列出 `pending_approval=1` 的条目——**模型推断出来、等用户确认的**。
响应是数组；没有待确认项时返回空数组。

### POST `/profile/memories/{memory_id}/approve`

批准待确认条目：清掉 `pending_approval`，这条记忆才参与后续的画像注入。

### POST `/profile/memories/{memory_id}/reject`

拒绝并删除该条目，成功返回 **204 No Content**。

### GET `/profile/memory-logs`

查询参数 `limit`（默认 50，1~200）。返回记忆变更日志，倒序：

```json
[
  { "id": 30, "memory_id": 11, "category": 0, "category_label": "技能",
    "name": "Python", "action": "update", "action_label": "更新",
    "before_json": "{\"mastery\": 75}", "after_json": "{\"mastery\": 82}",
    "created_at": 1758000000 }
]
```

## 画像提案（先确认再写入）

面试 / 简历场景里模型会从对话中抽出画像信息，但**不直接写入**，
而是先落一条提案，等用户确认（这是 D11 的决策）。

### GET `/profile-proposals`

查询参数 `session_id`（必填）。返回该会话下的**全部**提案（含已确认 / 已忽略，
按创建顺序），**前端按 `status` 过滤**；这么设计是为了让前端刷新页面后能靠
`message_id → id` 映射把确认卡片挂回历史消息：

```json
{
  "items": [
    { "id": 6, "session_id": 12, "message_id": 345, "target_job": "后端开发",
      "years_experience": "3", "target_level": "中级",
      "target_skills": ["Redis"], "weak_topics": ["并发编程"],
      "status": 0, "created_at": 1758000000 }
  ],
  "total": 1
}
```

`status`：0=待确认，1=已确认，2=已忽略。

**提案是"一次性"的**：已确认 / 已忽略的提案再调 confirm 或 dismiss 会返回 **409**
（"这条画像信息已经处理过了"），不会重复写入画像。

### POST `/profile-proposals/{proposal_id}/confirm`

确认并写入画像。请求体各字段都可省略——**省略表示"不修改该项"**，
传了就覆盖：

```json
{ "target_job": "后端开发", "target_skills": ["Redis", "Kafka"], "weak_topics": ["并发编程"] }
```

响应里 `status` 变成已确认，`message` 是"画像已更新，之后的回答会参考这些信息"。

### POST `/profile-proposals/{proposal_id}/dismiss`

忽略这条提案（不写入画像），响应文案"已忽略这条画像信息"。

## 用户与鉴权

### POST `/auth/register`

```json
{ "username": "alice", "password": "smoke123456", "avatar": null }
```

`username` 3~20 字符，`password` 8~72 字符且**必须同时含字母和数字**、
不能包含用户名、不能是常见弱密码。成功返回 **201**。
限流：**5 次/分钟**。

### POST `/auth/login`

```json
{ "username": "alice", "password": "smoke123456" }
```

```json
{ "access_token": "…", "refresh_token": "…", "token_type": "bearer", "expires_in": 7200 }
```

账号不存在与密码错误返回**同一句话**（"用户名或密码错误"），避免账号枚举。限流 **10 次/分钟**。

### POST `/auth/refresh`

```json
{ "refresh_token": "…" }
```

返回新的访问令牌与刷新令牌（响应结构与登录一致）。限流 **30 次/分钟**。

- 两种令牌密钥相同、靠 `typ` 字段区分：拿**访问令牌**当刷新令牌用会被拒（401），
  否则等于绕过了短期令牌的有效期限制。
- 令牌失效或用户已删除，一律 401。

### GET / POST / PUT / DELETE `/users[...]`

标准 CRUD，全部需要登录。

- 列表返回 `{"users": [...]}`；
- 路径参数 `user_id` 必须 > 0，否则 422；
- 目标不存在 404，用户名被占用 409，空更新请求 400；
- **`DELETE /users/{id}` 会连带清掉该用户的全部数据**：会话、消息、笔记、画像、
  记忆与日志、题库与题目、面试与复盘、资源（对象存储在事务提交后 best-effort 回收）。
  顺序按外键依赖从叶子到根，`users` 被十几张表以 `NO ACTION` 外键引用、没有任何级联，
  漏掉任何一张都会撞外键。

## 提示词管理

### GET `/prompt/templates/{agent_name}/{scene}`

返回某智能体某场景下的全部模板版本（**按版本倒序**）：

```json
{ "code": 0, "message": "查询成功",
  "data": { "agent_name": "interview_host", "scene": "interview",
            "versions": [ { "id": 9, "version": 2, "is_active": 1, "...": "…" } ] } }
```

**查不到不是异常**：返回 `200 + code=0 + data=null + message="未找到模板"`，
前端靠 `data` 是否为空区分"没有历史版本"。

### POST `/prompt/rollback`

```json
{ "template_id": 9 }
```

回滚到指定版本：把同 `(agent_name, scene)` 的其他版本 `is_active` 置 0，
目标版本置 1，并刷新 Redis 缓存。模板不存在返回 **404**；
缺 `template_id` 返回 422。

### GET `/prompt/config/agents`

返回全部已登记智能体（名称 + 场景），用于管理端渲染：

```json
{ "code": 0, "message": "查询成功",
  "data": { "interview_host": { "scene": "interview", "name": "面试主考官Agent" } } }
```

> **风险**：这三个接口**目前完全没有鉴权**（router 没挂 `get_current_user`），
> 其中模板版本列表会返回模板正文全文。前端不调用它们，但公网可匿名访问。
> 已记为待办 **T10.8**。
